## Side channels and hedged signing

- The vector cards describe attack classes and the countermeasure techniques discussed for them. Whether a given HSM implements a technique is stated, if at all, in the vendor's documentation and the module's Security Policy. NIST SP 800-140F section 6.2 (March 2020) reads in full "No additional requirements at this time", so CMVP has no approved non-invasive test metrics. FIPS 140-3 IG 12.A: "If a cryptographic module has been purposely designed, built and publicly documented to mitigate one or more specific attacks, this section is applicable and AS12.01 through AS12.04 (as applicable) shall be addressed regardless if the vendor of the module wishes to address the claim or not."
- ML-DSA hedged signing, FIPS 204 section 3.4: hedged is the default variant; "The use of fresh randomness during signing helps mitigate side-channel attacks"; the deterministic variant "should not be used on platforms where side-channel attacks are a concern and where they cannot be otherwise mitigated". PKCS#11 v3.2 lets the caller choose CKH_HEDGE_PREFERRED, CKH_HEDGE_REQUIRED or CKH_DETERMINISTIC_REQUIRED, so which variant a given HSM uses by default is a property of that product (module documentation and Security Policy).

## Stateful signatures in an HSM

- NIST SP 800-208 section 8.1 (p. 28): "In order to prevent the possible reuse of an OTS key, when the cryptographic module accepts a request to sign a message, the cryptographic module shall increment the leaf index of the private key (q in LMS, idx in XMSS, idx_sig in XMSSMT) and shall store the incremented leaf index value in nonvolatile storage before exporting a signature value or accepting another request to sign a message." IG C.N Resolution 12 has the tester confirm it. How a product recovers after a power failure is product behaviour (Security Policy and administrator guide).

## What the lab tests (Learn > HSM Firmware Migration)

A PQC-capable HSM is checked in four places. CAVP is NIST's algorithm validation program (tests specified in ACVP documents). CMVP is NIST's cryptographic module validation program: a module's certificate lists its approved algorithms and the Security Policy published with it lists its services. A CAST is a cryptographic algorithm self-test run by a validated module; a PCT is a pairwise consistency test on a generated key pair; a CSTL is an accredited testing laboratory.

- Algorithm certificates (CAVP): NIST's ACVP specification drafts (2 October 2026) cover ML-KEM (keyGen, encapDecap), ML-DSA, SLH-DSA and LMS (keyGen, sigGen, sigVer). CAVP overview page: "Cryptographic algorithm validation is a prerequisite of cryptographic module validation." and "Due to this structure, ACVTS testing is entirely black-box. The implementation is never provided to NIST or the CAVP in order to receive a validation certificate." ML-KEM draft section 6.1: "For the encapsulation key check, the server will generate a potentially valid or invalid encapsulation key ek. The IUT SHALL determine if the provided ek is valid based on [FIPS203] Section 7.2." Not covered (ML-DSA draft section 6.2.2): "An ACVP server will not test the zeroization of intermediate values, security strength of the deterministic random bit generators (DRBGs), or incorrect length signatures or public keys." LMS draft section 6.2.2: "ACVP does not test the inability of an implementation to export a private key. ACVP does not provide any guarantees on the inability to reuse private OTS pairs of an implementation." IG C.N Background (last modified September 2024): "CAVP tests are undergoing development with testing available for LMS but not yet for XMSS, HSS, or XMSSMT." No ACVP specification is published for XMSS, XMSS^MT or HSS (October 2026).
- Module certificate (CMVP) and Security Policy: CAVP overview page: "For an algorithm implementation to be listed on a cryptographic module validation certificate as an Approved security function, the algorithm implementation must meet all the requirements of FIPS 140 and must successfully complete the cryptographic algorithm validation process. However, a product or implementation does not meet the FIPS 140 module validation requirements by simply implementing an Approved security function and acquiring validations for each of the implemented algorithms." A Security Policy keeps approved and non-approved items apart (the policy of CMVP #4703 has "Table 10 Approved Services" and "Table 11 Non-Approved Services" and lists non-approved algorithms in its Tables 4, 5 and 6). IG 2.4.A: "the algorithm shall be included in the Security Policy's list of non-approved algorithms allowed in the approved mode of operation with no security claimed (see SP 800-140B). However, the module's certificate shall not include these algorithms as they do not claim any security and are not used to meet any requirement of FIPS 140-3." The question to put to a certificate is whether ML-DSA (or ML-KEM, SLH-DSA, LMS) is among its approved algorithms and which approved services use it.
- Self-tests (FIPS 140-3 IG 10.3.A, last modified 19 August 2026): "The requirements of this IG apply prior to the first operational use of the cryptographic algorithm." GeneralNote8: "For all algorithms that require a CAST (e.g., approved algorithms, allowed algorithms with a claim of security as permitted by an IG, and legacy algorithms per IG C.M), a CAST shall be performed prior to first time algorithm execution in the approved mode; but CASTs are NOT required (but are certainly permissible) prior to first time algorithm execution in the non-approved mode." ML-KEM: "if the module implements ML-KEM encapsulation, the module shall have a CAST for the ML-KEM encapsulation mechanism." and Note21: "The ML-KEM decapsulation CASTs shall cover both the implicit rejection and (unnamed) non-rejection paths." ML-DSA: "if the module implements digital signature generation, the module shall have an ML-DSA digital signature generation CAST for either the 'hedged' or 'deterministic' algorithm (per FIPS 204 Section 5.2)." LMS: "If the module implements LMS signature generation then it shall also implement key generation and shall have CASTs for both LMS signature generation and key generation." Pairwise consistency test (Additional Comments 1): "Though not a CAST, a pairwise consistency test (PCT) shall be conducted for every generated public and private key pair for the applicable approved algorithm (per ISO/IEC 19790:2012 Section 7.10.3.3)." For ML-KEM the PCT encapsulates a shared secret K with ek and decapsulates with dk, and passes if the two K values are equal. For key pairs generated from stored seeds (FIPS 203, FIPS 204) a PCT is only required prior to the first exportation of the seed or key pair or prior to the first operational use of the key pair after the seed has been generated within the module. IG D.S Scenario 1 (last modified 9 April 2026): "ML-KEM shall be CAVP tested via 'ML-KEM EncapDecap' for all implemented parameter sets (ML-KEM-1024, ML-KEM-512, ML-KEM-768) and functions (Decapsulation, Encapsulation). The module shall implement the encapsulation and decapsulation key checks specified in FIPS 203 Sections 7.2 and 7.3".
- Which submission for a firmware update (CMVP Management Manual version 2.7, 9 April 2026, section 7.1; twelve submission scenarios): "An updated version of a previously validated cryptographic module can be considered for a revalidation rather than a full validation depending on the extent of the modifications from the previously validated version of the module." Full Submission (FS): "If modifications are made to hardware, software, or firmware components that do not meet any of the below revalidation criteria, then the cryptographic module shall be considered a new module and shall undergo a full validation testing by a CSTL and submitted as a FS." Algorithm Update (ALG): "Code or configuration changes are not permitted under this revalidation scenario." CVE: "Changes shall not introduce new features or cryptography". Update (UPDT): "An updated cryptographic module can be considered in this scenario if less than a 30% of security changes were made to the module. Security changes include impacts to: approved / allowed security functions/algorithms, SSPs, approved security services, self-tests, and security states within the FSM. None of these, assessed individually, can exceed 30% of changes." and "The CMVP upon review, may determine that the changes are >30% and shall be submitted as an FS." The summary table (section 7.1.14) gives UPDT a new certificate and a new sunset date and requires the latest guidance, CAVP testing and, where IG 9.3.A applies, ESV testing. Adding ML-KEM, ML-DSA or SLH-DSA changes the approved algorithms, approved services and self-tests, which are categories counted toward the 30% limit; whether a given release is an UPDT or an FS is decided by the CMVP on the lab's submission.
