# SLH-DSA Module (FIPS 205)

The SLH-DSA module covers FIPS 205 (Stateless Hash-Based Digital Signature Standard), NIST's standardized stateless hash-based signature scheme. Unlike stateful schemes (LMS, XMSS), SLH-DSA requires no per-key state tracking — it can be safely deployed in distributed, serverless, and multi-instance environments. Security relies on the presumed difficulty of finding preimages for the underlying hash functions (SHA-256, SHA-512, or SHAKE256) as well as several related properties of those functions (FIPS 205 §1.1). FIPS 205 §10.2 says that even if it is feasible to compute collisions on them, there is believed to be no adverse effect on the security of SLH-DSA, although applications that require message-bound signatures may be adversely affected if collisions on H_msg are feasible (§11). Likewise, if the input to the signing function is a digest of the content, then collisions on the function used to compute the digest can result in forged messages (§10.2, footnote 19). The module covers the full FIPS 205 specification: WOTS+ one-time signatures, FORS few-time signatures, hypertree construction, the twelve parameter sets from Table 2, context strings for domain separation, deterministic signing mode, and the HashSLH-DSA pre-hash variant.

## Key Concepts

Organizational-control example: set a maximum signing-key lifetime and rotate on schedule; inventory deployments, copies and backups; conservatively estimate aggregate signing volume over that lifetime and revisit changes; preserve the original retirement date after backup restore. These controls document expected use below the analysis bound, not an enforced exact count. This is practical planning guidance, not a FIPS 205-prescribed checklist or sufficient certification evidence by itself.

Keep planned use within the FIPS 205 analysis bound: even one billion signatures per second with the same key would take about 585 years to reach 2^64. Exact technical enforcement is difficult across key copies and devices: a local HSM counter is insufficient, and coordinated accounting must resist backup-restore resets and rollback. No HSM enforcement has been verified in this review. A practical planning approach is to conservatively bound total signing volume across all copies over the key lifetime, far below the limit; this is not a recommendation to add an LMS/XMSS-style per-signature counter.

- SLH-DSA is stateless (FIPS 205 §3): a key pair is a very large set of few-time FORS keys; each signature computes a randomized hash of the message, uses part of the digest to pseudorandomly select one FORS key, and authenticates it with a hypertree signature, so there is no leaf counter as in LMS/XMSS. The security of a FORS key degrades gradually as the number of signatures increases (§8), and the parameter sets are designed for at most 2^64 signatures per key (§11)
- WOTS+ (Winternitz OTS Plus): one-time signature component; signs a message digest by hashing chains of n-byte values; the Winternitz parameter lg_w=4 is fixed in FIPS 205; chain lengths balance signature size vs. hash-round cost
- FORS (Forest of Random Subsets): the few-time signature layer between WOTS+ and the hypertree; signs a k-subset of values using a-level hash trees; parameters (k, a) directly control signature size and security against multi-target attacks
- Hypertree: d layers of XMSS trees, each a Merkle tree of height h/d; the XMSS keys at the lowest layer sign FORS public keys, and the XMSS keys at every other layer sign the XMSS public keys at the layer below (FIPS 205 §7); the public key of the XMSS key at the top layer (PK.root), together with PK.seed, is the SLH-DSA public key (§3)
- The s vs. f tradeoff: -s (small) variants use fewer hypertree layers (lower d) producing smaller signatures but requiring more hash rounds per layer; -f (fast) variants use more layers for faster signing at the cost of larger signatures
- FIPS 205 Table 2 defines twelve parameter sets across three security levels (NIST Levels 1, 3, 5) and two hash families (SHA-2, SHAKE), with signature sizes ranging from 7,856 B (SHA2-128s) to 49,856 B (SHAKE-256f)
- Context strings (FIPS 205 §10.2): an optional byte string bound into the signature; provides domain separation between protocols; verification with a different context string produces CKR_SIGNATURE_INVALID even for a valid (SK, M) pair
- Deterministic versus hedged signing (FIPS 205 §9.2): identical key, message, context and settings produce identical deterministic signatures; hedged signing adds fresh randomness and normally produces different signatures. Both should verify. Comparing signatures demonstrates mode behavior, not random-generator quality or resistance to attacks. Deterministic signing still requires randomness for key generation. Internally opt_rand uses the public PK.seed value, not zeros.
- HashSLH-DSA (FIPS 205 §10.2.2, Algorithm 23): hashes the message with the selected pre-hash function and constructs M' = 0x01 || len(ctx) || ctx || OID_DER || H(M). Context strings of 0–255 bytes are permitted; verification uses the same context (§10.3, Algorithm 25). The live demo now exposes separate signing and verification contexts, empty by default, for pure and fixed-hash pre-hash modes. UTF-8 byte lengths are shown, whitespace is preserved, and overlong inputs are rejected. Tests of the shipped Rust WASM cover matching/mismatched contexts and length boundaries for SHA2-128f pure and SHA-256 pre-hash, plus an upstream pre-hash reference signature. This is not a full conformance claim for every parameter combination.
- Signing capacity: SLH-DSA needs no persistent leaf counter, but FIPS 205 §11 bases the security claims for its 12 parameter sets on at most 2^64 messages per key pair. This is an assumption of the security analysis, not a requirement to persist an LMS/XMSS-style counter, and not a prediction of immediate failure beyond the limit. Absence of a leaf counter does not remove key-management obligations.

## What the lab tests (validation)

The Learn tab (HashSLH-DSA Modes step) has a "What the lab tests" panel with these facts. A validated SLH-DSA module is checked in three separate ways: algorithm tests, the module's own self-tests, and the certificate path. Whether the algorithm may be used at all for national security systems is answered by CNSA 2.0.

- Algorithm tests (NIST ACVP, draft specification of 2 October 2026): SLH-DSA has three modes, keyGen, sigGen and sigVer, all against FIPS 205, each with one test type, AFT (Algorithm Functional Test). keyGen: generate a key pair from the provided seed and key values (SK.seed, SK.prf and PK.seed); the server provides at least 10 tests for each combination of capabilities. sigGen: generate a valid signature from the provided private key, message, context (external interface testing) and randomness (non-deterministic signing); at least 13 tests for each combination. sigVer: the server makes its tests by modifying a valid signature: a modified message, a modified signature (R, SIGFORS or SIGHT), a signature that is too long or too short, plus the valid case.
- ACVP capability options a vendor registers: parameterSets (any of the 12 names, SLH-DSA-SHA2-128s through SLH-DSA-SHAKE-256f); signatureInterfaces ("internal", "external"); preHash ("pure", "preHash", described as "Whether SLH-DSA or HashSLH-DSA are supported"), with hashAlgs used if preHash; deterministic (sigGen only), where "A value of 'true' indicates that deterministic signature generation is supported and a value of 'false' indicates that non-deterministic signature generation is supported"; messageLength (8 to 65536 bits, step 8) and contextLength (0 to 2040, step 8) as ranges. sigVer has signatureInterfaces and preHash but no deterministic field.
- Not tested by ACVP, in the specification's words: "that fresh seed values are used for fresh invocations of key generation, that approved deterministic random bit generators (DRBGs) are used with the correct security strengths, that sensitive data is destroyed, that key validation is performed, and that floating point arithmetic is not used."
- Module self-tests (FIPS 140-3 IG 10.3.A item 16, document updated 19 August 2026): for each of signature generation, signature verification and key generation that the module implements, a cryptographic algorithm self-test (CAST) runs before the algorithm's first use in the approved mode. The signature generation CAST is a known-answer test with fixed values compared with a pre-computed signature (SIG); the verification CAST checks that a known signature verifies (returns true); the key generation CAST uses fixed SK.seed, SK.prf and PK.seed and compares the private key ("as the private key contains a copy of the public key"). Notes 27 and 28: if pure and pre-hash SLH-DSA signature generation (or verification) are both implemented and "they both share the same underlying cryptographic implementations, a CAST on either one of them is sufficient to meet the CAST requirements for both". Note 29: a module that supports both SHA2 and SHAKE parameter sets in the approved mode runs the CASTs on at least two parameter sets, one SHA2 and one SHAKE; a module with one family needs at least one; testing at least one "s" and one "f" set is recommended but not required. Note 30: the CASTs need only exercise the smallest parameter set (lowest height trees) the module supports. The pairwise consistency test for FIPS 205 keys "may be limited to confirming the same key identifier (I in the case of LMS, SEED in the case of XMSS and PK.SEED for SLH-DSA) is shared by the resulting public and private key following generation".
- Certificate path (NIST CAVP page): "Cryptographic algorithm validation is a prerequisite of cryptographic module validation." But "a product or implementation does not meet the FIPS 140 module validation requirements by simply implementing an Approved security function and acquiring validations for each of the implemented algorithms." ACVTS testing "is entirely black-box. The implementation is never provided to NIST or the CAVP", and CAVP "is not responsible for running those test vectors through the implementation". The CASTs are a FIPS 140-3 module requirement set by CMVP guidance (IG 10.3.A), separate from the ACVP tests.
- CNSA 2.0 status (NSA CNSA 2.0 FAQ, version 2.2, October 2026): "While SLH-DSA is hash-based, it is not part of CNSA and is not approved for any use in NSS." For national security systems the list of deployment contexts where SLH-DSA's trade-offs are usually acceptable (code signing, firmware attestation) does not apply. The CNSA 2.0 algorithm table lists ML-DSA-87 for digital signatures and LMS and XMSS (NIST SP 800-208) for signing firmware and software; see the Stateful Hash Signatures module for how those are validated (verify-only products need CAVP testing alone, signers that are NSS need hardware validated by CMVP or, in the FAQ's words, "via other NSA guidance"; waivers are not granted).

## Workshop Activities

- **Step 1 -- Key Generation & Parameter Explorer**: Generate SLH-DSA key pairs across all twelve FIPS 205 parameter sets; observe how n, h, d, k, a determine key size, signature size, and the security-performance tradeoff
- **Step 2 -- Sign & Verify (Pure + HashSLH-DSA)**: Sign messages with Pure SLH-DSA (CKM_SLH_DSA) and HashSLH-DSA (CKM_HASH_SLH_DSA_SHA256); observe the PKCS#11 mechanism change and the pre-hash payload construction
- **Step 3 -- Context Strings & Deterministic Mode**: Demonstrate matching and mismatched contexts using separate fields; empty and a space differ. Expected signature rejection is distinct from an engine error. Explicit deterministic-required and hedged-required signing choices now drive the existing demo. “Sign twice and compare” signs identical inputs twice, compares full signature bytes and verifies both; expandable hex shows both signatures. Saved inputs/mode accompany results. This demonstrates behavior, not RNG quality, attack resistance or certification compliance.
- **Algorithm checks (workshop Steps 1-3)**: the panels are kept apart by the kind of evidence they give. Known-answer checks compare the engine with a value fixed in advance: a SHA-256 NIST sample, and a replay of eight published NIST ACVP sigVer cases (SLH-DSA-SHA2-128s test group 19, test cases 253, 256, 260, 262 and 266; SLH-DSA-SHAKE-128s test group 25, test cases 338, 343 and 344; pure SLH-DSA, external interface; from the public NIST ACVP-Server repository, commit 975de31) through the in-browser engine. The valid signatures must be accepted and the ones NIST marks invalid (modified message, modified signature R or SIGFORS, signature too short or too long) rejected, as NIST's expected result says. The SLH-DSA sign-and-verify rows are functional round trips, not known-answer tests: the engine verifies its own output, so a pass shows the pieces work together and nothing more. The ACVP cases are public reference samples, not vectors issued by an ACVTS test session, so a pass establishes no validation. Pre-hash, internal-interface, key-generation and signature-generation vectors are not run in these panels. The intro of this demo points to Step 4 of this module for the comparison; the LMS checks live in the Stateful Hash Signatures module.
- **Step 4 -- LMS vs XMSS vs SLH-DSA Comparison**: Side-by-side comparison of all three hash-based signature families on key size, signature size, signing speed, state requirement, and deployment model. The size rows name their parameter sets (LMS_SHA256_M24_H10 / LMOTS_SHA256_N24_W4, XMSS-SHA2_10_192, SLH-DSA-SHA2-192s and -192f) and compare size classes, not equal security, because SP 800-208 assigns no NIST category to LMS or XMSS: LMS public key 48 B and signature 1,500 B (RFC 8554: public key 4 + 4 + 16 + m bytes, signature 12 + n(p + 1) + m*h bytes), XMSS 52 B and 1,492 B (RFC 8391), SLH-DSA-SHA2-192s 48 B and 16,224 B, -192f 35,664 B (FIPS 205 Table 2). CNSA 2.0 row (NSA FAQ version 2.2): single-tree LMS and XMSS are approved for firmware and software signing, HSS and XMSS^MT are not allowed, and SLH-DSA is not approved for any use in NSS.

## Related Standards

- FIPS 205 (SLH-DSA Stateless Hash-Based Digital Signature Standard, August 2024)
- FIPS 204 (ML-DSA, lattice-based alternative), SP 800-208 (LMS/XMSS stateful counterparts)
- PKCS#11 v3.2: CKM_SLH_DSA, CKM_HASH_SLH_DSA_SHA256, CKM_HASH_SLH_DSA_SHA384, CKM_HASH_SLH_DSA_SHA512, CKM_HASH_SLH_DSA_SHAKE128, CKM_HASH_SLH_DSA_SHAKE256
- CNSA 2.0 (NSA CNSA 2.0 FAQ, version 2.2, October 2026): "While SLH-DSA is hash-based, it is not part of CNSA and is not approved for any use in NSS." The CNSA 2.0 algorithm table lists ML-DSA-87 for digital signatures and LMS and XMSS (NIST SP 800-208) for signing firmware and software.
- FIPS 140-3 Implementation Guidance 10.3.A (document updated 19 August 2026): self-test (CAST) requirements for SLH-DSA, item 16
- BSI TR-02102-1 (German Federal Office; recommends SLH-DSA-SHA2-192s or stronger for long-term security)
- ANSSI (PQC position of 2022 and PQC FAQ of 2025): the only post-quantum algorithms for which ANSSI does not recommend systematic hybridisation are the hash-based signatures SLH-DSA, XMSS and LMS; the 2022 position estimates they could be used today without hybridisation, however their potential application range is limited (low number of signatures queries or large signature sizes); for the regulated scope the FAQ says hybridisation is mandatory
