# Hybrid and Composite Cryptography

## Overview

The Hybrid Cryptography module teaches how to combine classical and post-quantum algorithms during the quantum transition, and what that choice costs. It runs in this order: why hybrid; the risks of hybrid compared with pure PQC, for key establishment and for signatures; which national agencies, standards bodies and companies recommend hybrid or accept pure PQC; hybrid KEM construction (X25519MLKEM768, combiners); hybrid KEMs in TLS 1.3; implementation and validation (SP 800-227, FIPS 140-3 IG D.S); HPKE; hybrid signatures (non-separability, Silithium); and finally hybrid certificates (seven X.509 formats plus chameleon certificates as a historical design).

## Key Concepts

- **Hybrid cryptography** combines classical and PQC algorithms so that security holds even if one component is broken
- **Pure PQC risks (what hybrid guards against)**: young schemes can fall to classical cryptanalysis (SIKE and Rainbow, per the Czech NÚKIB annex); in 2026 the BSI advised against Classic McEliece in new developments after new structural cryptanalysis and noted that a hybrid with Classic McEliece still keeps at least classical security; new implementations can carry exploitable bugs (Bernstein 2026: a small change in ML-DSA software is exploitable in 1 second on 1 laptop core, and far fewer Ed25519+ML-DSA keys than ML-DSA-only keys are estimated to be breakable for years after the first quantum attack)
- **Risks of hybrid KEMs**: an unsound combiner (ETSI TR 103 966: a "concatenation only" hybrid key is not secure against active adversaries; SP 800-227 approves specific combiners); fallback to classical-only when a client retries after a failed hybrid attempt (backwards-compatible hybrids can be open to downgrade, ETSI TR 103 966); larger messages (X25519MLKEM768 key share 1,216 bytes vs 32) and, in IKEv2, extra pre-authentication key exchanges raising denial-of-service risk; HPKE Auth modes cannot use ML-KEM or hybrids containing it; FIPS 140-3 approval only under the five IG D.S conditions (X-Wing cannot yet meet them)
- **Risks of hybrid signatures**: stripping one signature when verifiers accept either component (ETSI TR 103 966: such a backwards-compatible hybrid can be less secure than the PQC algorithm alone; fix: require both, or a non-separable construction per RFC 9955); certificate rollback where a server keeps classical certificates (individual draft draft-sheffer-tls-pqc-continuity proposes clients remember PQC support); more complex and less researched than hybrid confidentiality (UK NCSC); a PKI that issues both signature types or two parallel PKIs (NCSC prefers a single migration to a fully post-quantum PKI; the NSA tells national security systems to use a parallel PKI, not several algorithms in one certificate); no universally accepted hybrid certificate format (GSMA PQ.03 finds recommending hybrid certificates premature); composite ML-DSA-65 + ECDSA P-256 signatures of about 3.4 KB; no FIPS 140-3 IG section on composite signatures
- **Risks common to both**: added complexity and attack surface (NSA: more products fail through implementation or configuration errors than through algorithms; Dutch PQC Migration Handbook: hybridisation may increase attack surface); every party must support all components and the same combination method; removing the classical part later is a second transition; for some formal properties hybrids may be no stronger, or even weaker, than their components (NSA: a matter of significant debate); something marketed as hybrid is not necessarily quantum resistant; overhead of two algorithms, judged low when hybrid only sets up a session key (Dutch handbook)
- **Who recommends hybrid**: ANSSI (France) insists on hybrid wherever PQC is deployed in the short and medium term, mandatory in the French regulated perimeter, except hash-based signatures (SLH-DSA, XMSS, LMS); its recommendations are not a regulatory obligation elsewhere. BSI (Germany) TR-02102-1 currently recommends quantum-safe methods only in hybrid use; classical-only key agreement is recommended until the end of 2031. The Dutch AIVD/CWI/TNO handbook recommends hybrid especially when deploying before mature implementations exist. The EU ECCG Agreed Cryptographic Mechanisms v2.0 recommends hybrid mode for long-term confidentiality (the v3 draft adds that lattice mechanisms should not be used standalone); ENISA's 2026 hybridization report is explicitly not a recommendation
- **Who accepts pure PQC**: the NSA will not require hybrid for national security systems and counts only NSA-identified hybrids (such as its IKEv2 profile) as CNSA 2.0 compliant; the UK NCSC uses hybrid only where needed (interoperability, implementation security, protocol constraints); the Czech NÚKIB accepts hybrid or standalone ML-KEM and ML-DSA at security level 5; NIST approves ML-KEM and ML-DSA on their own and says combining can be advantageous during migration (SP 800-227); Canada's Cyber Centre (ITSP.40.111 version 5) recommends ML-KEM and ML-DSA and phases out classical schemes used without a post-quantum scheme by the end of 2035, without discussing hybrid
- **Standards bodies and industry**: ETSI specifies hybrid key exchange (TS 103 744) and describes trade-offs (TR 103 966) without mandating it; the IETF standardizes both hybrid TLS groups (RFC 10024) and pure ML-KEM groups (draft) and does not choose for deployers; Google Chrome, Cloudflare and AWS deploy X25519MLKEM768; Cloudflare targets 2029 for full post-quantum security including authentication
- **NIST SP 800-227** describes how to combine key-establishment mechanisms securely (§4.6): a suitably designed classical/PQC combination can retain security if one component remains secure. Compatibility with existing systems depends on the protocol and the mechanisms each participant supports — the combination itself does not provide it. §3.3 recommends appropriate side-channel protections such as constant-time implementations; migration to pure PQC is driven by algorithm maturation rather than calendar deadlines alone
- **SP 800-227 approved KEM parameter sets**: ML-KEM-512 → NIST Category 1 (AES-128 equivalent, constrained/IoT, short-lived sessions); ML-KEM-768 → Category 3 (AES-192 equivalent, default for TLS 1.3 and most internet traffic); ML-KEM-1024 → Category 5 (AES-256 equivalent, CNSA 2.0 and high-assurance/federal systems). This module's rule of thumb, not from a standard: HNDL risk and data-retention window should drive the choice, and ciphertext that must stay secret past ~2035 should use Category 3 or 5 rather than Category 1
- **Hybrid KEM in a FIPS 140-3 validated module (CMVP IG D.S, last modified 9 April 2026)**: IG D.S "Scenario 2" is a hybrid of an approved ML-KEM plus one or more non-ML-KEM schemes combined through an approved key combiner (SP 800-227 §4.6.2); the non-ML-KEM may be approved or non-approved (examples: X25519, X448). To claim Scenario 2, a module must implement at a minimum all five of: (1) an approved ML-KEM; (2) one or more non-ML-KEM (approved or non-approved); (3) an approved key combiner (a concatenation of the shared secrets fed into an SP 800-56C one-step or two-step KDF, HKDF included, or an SP 800-133 §6.3 method: concatenation, XOR, or key extraction using HMAC; the IG describes the §6.3 route only for combining ML-KEM shared secrets with those of approved key-agreement schemes, IG D.F Scenario 1 or 2); (4) the module does not offer arbitrary hybrid combinations but enforces a pre-defined set of hybrid schemes (e.g., SecP256r1MLKEM768, X25519MLKEM768, SecP384r1MLKEM1024); (5) for each set, the module controls at minimum the shared-secret sequencing logic (e.g., concatenation order). If any is missing (e.g., a library with an approved ML-KEM and X25519 but no approved key combiner, or one with the first three items that does not enforce a set of combinations or control sequencing), Scenario 2 cannot be claimed and any non-approved non-ML-KEM scheme offered must be restricted to the non-approved mode only. A non-approved component such as X25519 is classified as a "non-approved but allowed algorithm with no security claimed" (IG 2.4.A; listed in the Security Policy, not on the certificate); it may be used only inside the approved hybrid, enforced by the module itself (not used for other purposes in approved mode, not offered as an independent approved service such as a separate API call in a software library; operator guidance in the Security Policy cannot enforce it). The claimed security strength of the hybrid comes from the ML-KEM, and the hybrid service is then an approved security service. The Security Policy records the claim in the Security Function Implementation table as "KEM-Hybrid" or "KEM-Hybrid-Full" (entry names such as "KEM-Hybrid X25519MLKEM768"); the non-approved half is listed with the caveat "no security claimed" citing IG D.S Scenario 2 and IG 2.4.A (CMVP KEM Hybrid guidance, last updated 8 April 2026). "KEM-Hybrid" applies when a module meets items 1 to 5 but not the extra conditions for "KEM-Hybrid-Full", and it can still be an approved service, even for a software library offering it to a calling application. IG D.S Additional Comment 8: the TLS 1.3 hybrid key exchange (draft-ietf-tls-ecdhe-mlkem-01, now RFC 10024) may meet Scenario 2 using the SP 800-56C HKDF as the approved combiner with one of SecP256r1MLKEM768, X25519MLKEM768 or SecP384r1MLKEM1024 (the specifications may still be in draft form); the X-Wing hybrid KEM "cannot yet meet the requirements of Scenario 2" even though it uses an SP 800-56C one-step KDF, because at a minimum SP 800-133 needs an update to approve the X-Wing seed generation method (seed expansion using SHAKE is not currently in SP 800-133). Separately, the CAVP prerequisites page (updated 22 September 2026) lists X-Wing keyGen and encapDecap tests; CAVP states that acquiring validations for each implemented algorithm does not by itself meet the FIPS 140 module requirements. Self-tests: every approved scheme in the hybrid must be self-tested individually under IG 10.3.A; for the ML-KEM part, under IG 10.3.A (known-answer self-tests for each ML-KEM function implemented: encapsulation, decapsulation, key generation; decapsulation tests cover both the implicit-rejection and non-rejection paths; on at least one of ML-KEM-512, -768 or -1024 as implemented in approved mode); IG D.S says there is currently no separate self-test for the approved key combiner or for the non-approved half, beyond self-testing any approved algorithms used within (e.g., KDFs). CAVP testing: the IG lets the approved pieces be tested separately (the ML-KEM and, with a non-approved other half, the approved algorithms beneath it such as KDFs), or end-to-end tests of the full hybrid scheme "if available within CAVP", with the IG to be updated after they become available; no hybrid-KEM specification appears in the ACVP specification index (pages.nist.gov/ACVP) as of 23 October 2026. Do not confuse with IG 1.B "Hybrid Modules" (new 19 August 2026), which concerns a module whose boundary combines a software or firmware component with a disjoint hardware component and has nothing to do with hybrid key exchange
- **Hybrid combiner construction (SP 800-227 + SP 800-56C-Rev2)**: concatenation order is fixed per protocol (TLS 1.3 per RFC 10024 §4.3: X25519MLKEM768 uses `ML-KEM_ss || X25519_ss`, while SecP256r1MLKEM768 and SecP384r1MLKEM1024 use `ECDHE_ss || ML-KEM_ss`; per its §5, SP 800-56C-Rev2 approves this when the first secret comes from a FIPS-approved scheme, so ML-KEM goes first where X25519 is used, and ECDHE goes first for the NIST curves, whose certified implementations are more widely available; SP 800-227 §4.6.2, September 2025, approves its key combiner when at least one shared secret in any position comes from an approved scheme); SP 800-56C permits either HKDF (HMAC-based extractor with SHA-256/384/512) or KMAC128/256 as the combiner; dual-PRF assumption means the combined secret is safe as long as _either_ input looks uniform to the attacker, so a future break of ML-KEM or of X25519 alone does not break the session key; SP 800-227 §4.6.3 says the domain-separation input should be used to uniquely identify the composite scheme in use (for example the two component schemes, order of composition, choice of parameter set, key combiner, KDF)
- **Combiners compared**: TLS 1.3 hybrid groups (RFC 10024) feed the concatenated secrets into the TLS 1.3 HKDF key schedule and rely on the handshake transcript to bind the key shares; X-Wing (draft-connolly-cfrg-xwing-kem-11) computes SHA3-256(ss_M || ss_X || ct_X || pk_X || XWingLabel), hashing the X25519 ciphertext and public key but not the ML-KEM ones; composite ML-KEM (draft-ietf-lamps-pq-composite-kem-23) uses the same shape, SHA3-256(mlkemSS || tradSS || tradCT || tradPK || Label), for twelve pairings, and its MLKEM768-X25519 entry uses the X-Wing label (hex 5c2e2f2f5e5c); the CFRG concrete hybrid KEMs (draft-irtf-cfrg-concrete-hybrid-kems-04) use SHAKE256 as PRG and SHA3-256 as KDF and state that MLKEM768-X25519 is identical to X-Wing; ETSI CatKDF (TS 103 744) forms psk || k1 || k2 and runs one KDF (HMAC, KMAC or HKDF) with a context holding all public keys and ciphertexts of both components, which the composite draft calls the more conservative choice, while CasKDF chains one KDF stage per component
- **What makes X-Wing different**: it leaves out the ML-KEM ciphertext and public key, relying on the specifics of ML-KEM-768's Fujisaki-Okamoto transform; the draft warns the combiner "cannot be assumed to be secure, when used with different KEMs"; if SHA3-256, SHA3-512 and SHAKE-256 are modelled as random oracles its IND-CCA security is bounded by ML-KEM-768's and the gap-CDH security of Curve25519; it claims MAL-BIND-K-PK and MAL-BIND-K-CT, which ML-KEM alone does not achieve; its private key is a 32-byte seed expanded with SHAKE256 into both component keys (public key 1,216 bytes, ciphertext 1,120 bytes, shared secret 32 bytes), the reason FIPS 140-3 IG D.S says it cannot yet meet Scenario 2; the composite ML-KEM draft calls X-Wing and its MLKEM768-X25519 entry "largely interchangeable", the one difference being X-Wing's joint seed keygen, so an X-Wing implementation is a compliant composite implementation but not the reverse
- **ML-KEM decapsulation and implicit rejection (FIPS 203 §§6.3 and 7.3)**: input checks can fail; for example, ML-KEM-768 requires a 1,088-byte ciphertext. After the required checks pass, an internal re-encryption mismatch selects a fallback shared secret derived from the secret rejection value `z` and the received ciphertext, without exposing the mismatch through an error or timing. Normal library argument and operational errors still apply. If tampering triggers this path, the receiver obtains a different secret; in a protocol deriving an AES-GCM key from it, authentication fails and unauthenticated plaintext must not be released. Implicit rejection conceals the internal ciphertext-validity result; a later authentication failure can also occur after valid decapsulation and does not directly disclose that result. Protocol error handling and timing must preserve this distinction. Successful decapsulation alone does not confirm a shared key: use protocol authentication or key confirmation.
- **Implementation considerations**: correct results alone do not show that an implementation protects its secrets; constant-time techniques help prevent execution time or memory access from revealing secret values, but do not mean every call takes the same number of milliseconds (SP 800-227 §3.3 recommends appropriate protections; effectiveness depends on the implementation and device). ML-KEM encapsulation requires fresh, unpredictable random input: an attacker who knows the 32-byte `m` can reproduce the encapsulation with the recipient's public key and recover the shared secret (FIPS 203 §3.3). In an X25519 + ML-KEM hybrid, a leak of only the X25519 secret can still be covered by a suitable combiner through the uncompromised ML-KEM secret; a leak of both secrets or the final session key loses that protection. For HSM/TPM devices, check the manufacturer's documentation for which protections exist and which settings affect them — do not assume a PQC-protection switch exists
- **CNSA 2.0** (NSA): its FAQ (v2.2, October 2026) quotes CNSSP 15 as requiring CNSA 2.0 algorithms in all new NSS acquisitions by 1 January 2027, says that by 31 December 2030 NSS equipment and services that cannot support CNSA 2.0 must be phased out unless otherwise granted an exception, and that by 31 December 2031 CNSA 2.0 algorithms are mandated for use, unless otherwise noted; it also says specific deadlines depend on equipment type; NSA will not require NSS developers to use hybrid certified products for security purposes, although product availability and interoperability requirements may lead to adopting hybrid solutions in specific cases
- **RFC 9794** standardizes terminology for hybrid schemes — "composite" (single OID, both-must-verify) vs "non-composite" (parallel independent algorithms); establishes "PQ/T" (Post-Quantum / Traditional) naming
- **Subject key vs. certificate signature**: the subject public-key algorithm and the certificate-signature algorithm are independent. An ML-KEM key cannot sign, so an ML-KEM certificate is always issued by a separate signing-capable CA (ML-DSA, ECDSA, RSA). The ML-KEM subject key performs encapsulation/decapsulation; the issuer key signs the certificate
- **Seven certificate formats in the main comparison** (five signature formats + two KEM formats):
  - **Pure PQC (ML-DSA)** — standard single-algorithm X.509 using ML-DSA signatures; OIDs standardized in RFC 9881; the workshop is tested with OpenSSL 3.6.3
  - **Pure PQC (SLH-DSA)** — hash-based signature X.509 certificates; OIDs in RFC 9909; ANSSI does not recommend systematic hybridisation for hash-based signatures such as SLH-DSA, XMSS and LMS
  - **Composite (dual-algorithm)** — single composite OID identifies the algorithm pair; both signatures must verify; defined in draft-ietf-lamps-pq-composite-sigs-19, approved and in the RFC Editor queue (no RFC number yet)
  - **Alt-Sig / Catalyst** — classical primary cert with PQC key and signature in X.509 extensions (SubjectAltPublicKeyInfo 2.5.29.72, AltSignatureAlgorithm 2.5.29.73, AltSignatureValue 2.5.29.74); legacy verifiers ignore the extensions; defined in ITU-T X.509 (2019) §7.2.2 and §9.8; relying-party policy decides whether one or both signatures are required
  - **Related Certificates (RFC 9763)** — a NEW certificate (Cert B) carries a RelatedCertificate extension holding the hash of the complete final DER of an EXISTING certificate (Cert A); the binding is one-way and Cert A is never modified; the CA issues Cert B only after a relatedCertRequest proves possession of Cert A's key; a protocol may use either certificate or both — RFC 9763 does not require both
  - **Pure PQC KEM (ML-KEM, RFC 9935)** — an ML-KEM public key in X.509; if keyUsage is present, keyEncipherment must be the only bit; the certificate is CA-issued, never self-signed; the key is used e.g. in CMS KEMRecipientInfo (RFC 9629, ML-KEM in CMS: RFC 9936)
  - **Composite KEM** — ML-KEM plus a classical KEM under one OID, ML-KEM first; defined in draft-ietf-lamps-pq-composite-kem-23, approved by the IESG and in the RFC Editor queue since 2026-10-12 (not yet an RFC)
- **Advanced examples (outside the main comparison)**: Certificate Discovery (draft-ietf-lamps-certdiscovery-03, active LAMPS WG draft) lets a primary certificate advertise in subjectInfoAccess where a related secondary certificate can be fetched and which algorithms it uses; a fetched secondary must still pass full path validation; the draft's OIDs are TBD, so the workshop uses documentation-arc placeholders (1.3.6.1.4.1.32473) and its encoding is illustrative. RFC 9925 unsigned certificates use id-alg-unsigned (1.3.6.1.5.5.7.6.36), a zero-length signature and a placeholder issuer (id-rdna-unsigned); they suit keys trusted by other means and are never valid in a certification path
- **Historical design — Chameleon Certificates**: a single cert with a DeltaCertificateDescriptor extension encoding the differences needed to rebuild a paired cert; draft-bonnell-lamps-chameleon-certs-07 is an expired individual draft never adopted by the LAMPS working group; kept for study only and not recommended for new deployments
- **Watchlist**: FN-DSA (planned FIPS 206, not yet final) has an IETF certificate draft, draft-ietf-lamps-fn-dsa-certificates, whose OIDs are still TBD — no deployable FN-DSA certificate exists yet
- **X25519MLKEM768** — the leading hybrid KEM combining Curve25519 ECDH with ML-KEM-768; enabled by default in Chrome 131 (November 2024), protecting most human traffic to Cloudflare by October 2025, and supported on AWS KMS, ACM and Secrets Manager endpoints (non-FIPS, April 2025); its shares and shared secret put the ML-KEM part first (ML-KEM_ss || X25519_ss, RFC 10024 §4.3), unlike SecP256r1MLKEM768 and SecP384r1MLKEM1024, which put ECDHE first
- **Other hybrid KEM variants**: SecP256r1MLKEM768 (P-256 + ML-KEM-768, FIPS-approved classical curve), SecP384r1MLKEM1024 (P-384 + ML-KEM-1024, NIST Level 5)
- **Composite signatures** combine ML-DSA with ECDSA or Ed25519 in a single operation; both must verify; single OID simplifies handling; prevents downgrade attacks
- **Size trade-offs**: composite signatures are approximately 3.4 KB versus 72 bytes for ECDSA alone
- **Hybrid KEMs in TLS 1.3**: X25519MLKEM768 integrates via the key_share extension; ClientHello key_share grows from 32 bytes (X25519) to 1,216 bytes (38× increase); may push ClientHello beyond a single TCP packet; Chrome reported about a 4% slowdown in TLS handshake time (as cited by Cloudflare, October 2025), and AWS measured a 0.05% (connection reuse) to 2.3% (new handshake per request) throughput drop for KMS (April 2025)
- **Hybrid TLS negotiation downgrade risk**: TLS 1.3's signed and MACed transcript detects an active MITM that removes the ML-KEM key_share from the ClientHello, but an attacker can make PQC attempts fail so that a client configured for compatibility fallback retries classical-only — even when both endpoints support hybrid; client-side memory of prior PQC support (PQ Lock, and the individual draft `draft-sheffer-tls-pqc-continuity`) limits this after a first successful PQC connection, covered in depth in the TLS 1.3 Basics module; composite signatures (single composite OID) prevent the analogous downgrade of authentication because both signature halves must verify together

## Workshop / Interactive Activities

The workshop has 7 hands-on steps:

1. **Hybrid Key Generation** — generate and compare classical, pure PQC, and hybrid key pairs, observing key size differences across categories. Its Known Answer area has a NIST ACVP panel for ML-KEM-768 (encapsulation with NIST's random value m, valid and modified-ciphertext decapsulation, and the FIPS 203 encapsulation-key and decapsulation-key checks, each answer compared with NIST's) and a table of further checks. Rows tagged "Functional" are round trips (the engine accepts its own output) with no published expected value; rows tagged "NIST ACVP sample" or "Standard KAT" compare with a published answer. None of it establishes a validation.
2. **Hybrid Encryption and Signing Demo** — after the key-establishment run, a comparison panel feeds the same two secrets through the demo's HKDF, the X-Wing / composite ML-KEM SHA3-256 combiner and a concatenation-only counter-example (which ETSI TR 103 966 says is not secure against active adversaries), and notes that the demo reads both secrets out of the token to show them, whereas a token can combine them with handles only (CKM_CONCATENATE_BASE_AND_KEY, CKM_CONCATENATE_BASE_AND_DATA, CKM_SHA3_256_KEY_DERIVATION). perform KEM encapsulation and digital signature operations in hybrid mode, comparing classical and PQC outputs. The key-establishment demo concatenates the two shared secrets, ML-KEM first (the RFC 10024 §4.3 order for X25519MLKEM768), and feeds the 64 bytes into HKDF-SHA-256 with no salt: the combiner form CMVP IG D.S accepts (a concatenation fed into an SP 800-56C KDF, HKDF included). Putting one secret in the HKDF salt and the other in the input is not that form. The demo binds no key shares or transcript and enforces no fixed set of hybrid schemes, so it is an illustration, not a validated design.
3. **HPKE** — RFC 9180 Hybrid Public Key Encryption composed from PKCS#11 v3.2 primitives: pick a KEM (classical DHKEM, ML-KEM or a PQ/T hybrid), KDF, AEAD and mode, and run Encap, KeySchedule, Seal and Open
4. **Hybrid Signatures** — concatenation, nesting and Silithium side by side, from no non-separability to the strong non-separability Silithium targets
5. **Hybrid CA Setup** — set up a hybrid certificate authority with both classical and PQC keys
6. **Hybrid Certificate Formats** — generate and compare seven X.509 formats: Pure PQC (ML-DSA-65), Pure PQC (SLH-DSA-128s), Composite (ML-DSA-65 + ECDSA), Alt-Sig/Catalyst (ECDSA primary + ML-DSA extensions), Related Certs (RFC 9763), Pure ML-KEM-768 (RFC 9935) and Composite ML-KEM; Chameleon is available separately under Historical designs. End-entity certificates for ML-DSA, SLH-DSA and both KEM formats are issued by a workshop CA in the browser HSM, and every result is checked (signatures, issuer chain, key usage) by an implementation other than the one that signed it
7. **Certificate Inspector** — deep-dive into generated certificates with Tree, Raw, and Size views; also inspect real IETF Hackathon reference certificates from the pqc-certificates test vector repository

## IETF Reference Certificates

The Certificate Inspector (Step 7) includes a toggle to view real DER-encoded hybrid certificates from trusted sources. Five test vectors are embedded:

- **Composite (MLDSA65-ECDSA-P256-SHA512)** — OID 1.3.6.1.5.5.7.6.45, generated by Bouncy Castle (IETF Hackathon r5); demonstrates composite OID backward incompatibility (OpenSSL shows "UNKNOWN")
- **Alt-Sig / Catalyst (ECDSA-P256 + ML-DSA-44 alt-sig)** — generated by Bouncy Castle (IETF Hackathon r5); uses alt-sig extensions 2.5.29.72 (SubjectAltPublicKeyInfo), 2.5.29.73 (AltSignatureAlgorithm), 2.5.29.74 (AltSignatureValue); classical primary with PQC in extensions
- **Pure ML-DSA-65** — OID 2.16.840.1.101.3.4.3.18, generated by OpenSSL 3.5 (IETF Hackathon r5); reference for FIPS 204 cert format
- **Pure SLH-DSA-SHA2-128s** — OID 2.16.840.1.101.3.4.3.20, from RFC 9909 Appendix C.3; hash-based signature cert (8,241 bytes); ANSSI does not recommend systematic hybridisation for it (ANSSI PQC FAQ 2025)
- **Chameleon (ECDSA-P256 outer + ML-DSA-44 delta)** — historical design (expired draft); generated by Bouncy Castle (IETF Hackathon r5); uses DeltaCertificateDescriptor extension 2.16.840.1.114027.80.6.1

Note: No official test vector exists for Related Certificates (RFC 9763) — the format is purely structural (a binding hash in an extension), not a cryptographic algorithm, so no KAT is applicable. The workshop generates RFC 9763 pairs programmatically.
