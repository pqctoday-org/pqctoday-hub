# Secure Boot & Firmware PQC

Module covering PQC migration for UEFI Secure Boot, firmware signing, TPM key hierarchies, and hardware attestation.

## Key Topics

- UEFI Secure Boot key hierarchy (PK/KEK/db) migration to ML-DSA-65 (this module's general-purpose target, NIST Security Level 3). For National Security Systems the NSA CNSA 2.0 FAQ (version 2.2, October 2026, algorithm table pp. 7-8) specifies ML-DSA-87 for all classification levels and allows LMS and XMSS (NIST SP 800-208) for signing firmware and software; HSS and XMSS^MT are not allowed and SLH-DSA is not approved for any use in NSS (p. 11). The key-hierarchy table in Learn shows a "CNSA 2.0 / NSS" column next to the ML-DSA-65 target. CNSA 2.0 also specifies SHA-384 or SHA-512, so the SHA-256 hashes in dbx are not the NSS choice.
- Signatures and attestation are a forgery risk ("trust now, forge later"), not harvest-now-decrypt-later: a signature protects no secret, so nothing recorded today is exposed later. Once a cryptographically relevant quantum computer exists, anyone holding a public key could derive the private key and forge firmware signatures or attestation evidence. Urgency follows how long the device and its trust anchors stay in the field; the CNSA 2.0 FAQ (p. 13) says "In many firmware-signing cases the validation algorithm is not easily updated. Thus, firmware-signing algorithms are frequently locked in for the life of a system." Harvest-now-decrypt-later applies to confidentiality, such as the TLS key exchange that carries remote attestation. The workshop's migration-urgency ratings and years-in-service figures are the module's own estimates, not measurements.
- Firmware signing with post-quantum algorithms
- TPM 2.0 path to post-quantum attestation
  - TCG published TPM 2.0 Library v185 on 12 March 2026; its Part 0 change history states "Introduced support for ML-DSA, HashML-DSA, and ML-KEM" (algorithm IDs TPM_ALG_MLKEM 0x00A0, TPM_ALG_MLDSA 0x00A1, TPM_ALG_HASH_MLDSA 0x00A2 in Part 2). TCG's 22 March 2026 announcement names ML-KEM for Endorsement Keys and ML-DSA for Attestation Keys; PC Client Platform TPM Profile 1.07 adds larger CRB data transport and defines which ML-KEM Endorsement Key certificates are required.
  - A TPM built to an earlier library version predates these algorithms (TPM2_GetCapability TPM_PT_REVISION and TPM_PT_ML_PARAMETER_SETS show what a part supports); for those TPMs the interim path is a hybrid of the RSA attestation key and a software ML-DSA key. Shipping silicon follows the specification, so check a vendor's own documentation for which version a part implements.
- Vendor roadmaps: AMI, Insyde, EDK2, Dell, HPE
- Hardware supply chain integrity at scale
- Firmware integrity checks beside the signature: NIST SP 800-193 (Platform Firmware Resiliency Guidelines) and the FIPS 140-3 software/firmware integrity test (Learn > Firmware PQC Migration)
- Boot-time signature verify latency on a microcontroller root of trust (Cortex-M4 class)

## What the lab tests (Learn > Firmware PQC Migration)

Firmware signing has two sides that are validated differently: the verifier (code on the device that checks the signature) and the signer (the module that holds the private key). CAVP is NIST's algorithm validation program (tests specified in ACVP documents), CMVP is NIST's cryptographic module validation program, and a CAST is a cryptographic algorithm self-test run by a validated module.

- Verifier, algorithm tests: NIST's ACVP specification drafts (2 October 2026) cover ML-DSA sigVer (ML-DSA / sigVer / FIPS204) and LMS sigVer (LMS / sigVer), both test type AFT. For LMS: "The ACVP server generates a series of signatures to communicate to the IUT. The IUT is REQUIRED to determine the validity of the signature given the tree structure, key, and message." For ML-DSA the server modifies a valid signature or message (modified message, or modified commitment, z or hint part); the ML-DSA draft says an ACVP server will not test "incorrect length signatures or public keys".
- No ACVP specification is published for XMSS, XMSS^MT or HSS (NIST's ACVP specification list, October 2026). FIPS 140-3 IG C.N (last modified 10 September 2024): "CAVP tests are undergoing development with testing available for LMS but not yet for XMSS, HSS, or XMSSMT." So CNSA 2.0 accepts XMSS as well as LMS, but of the SP 800-208 schemes only LMS has an ACVP test.
- Signer, SP 800-208 section 8.1: key generation and signature algorithms "shall only be validated for use within hardware cryptographic modules", validated to "FIPS 140-2 or FIPS 140-3 Level 3 or higher physical security", with a "non-modifiable or limited" operational environment, no export of private keying material, and the entropy source inside the module's physical boundary. The leaf index must be incremented and stored in nonvolatile storage before a signature is exported (IG C.N Resolution 8: this applies where all or part of the private key is held in non-volatile memory). IG C.N Resolution 1: modules that only verify follow section 8.2 and "do not need to meet requirements from section 8.1". The LMS ACVP draft says ACVP "does not test the inability of an implementation to export a private key" and gives no guarantee against reuse of private OTS pairs.
- NSA CNSA 2.0 FAQ (version 2.2, October 2026, pp. 11-12): "Signature verification is expected to be performed by code that has been validated by NIST's Cryptographic Algorithm Validation Program (CAVP). ... If your product is only verifying signatures, CAVP testing is all that is required." Signers: "Code sources and signature generation processes (signers) that are NSS are required to produce signatures according to NIST SP 800-208, which requires hardware validated by NIST's Cryptographic Module Validation Program (CMVP), or via other NSA guidance. Waivers for this will not be granted." For signers that are not NSS (for example many commercial vendors' development environments): "those signers are expected to use code in their signature generation processes that is at least at the same operational quality as the code being put on the device, but the only part NSA will validate is that the signature verification code on the device passes CAVP." For NIAP Protection Profile evaluations where signing happens outside the Target of Evaluation, the requirements "only apply to signature verification" and "only CAVP validation (not CMVP) will be expected to meet CNSA 2.0 for such products."
- CNSA 2.0 FAQ algorithm rules: LMS and XMSS "All parameters approved for all classification levels. LMS SHA-256/192 is recommended."; ML-DSA-87 is also listed for signing firmware and software; "The multi-tree algorithms HSS and XMSSMT are not allowed."; SLH-DSA "is not approved for any use in NSS". The FAQ advises implementing signing and state management in hardware such as an HSM, and says backup flows "must prevent state re-use".
- Module self-tests, FIPS 140-3 IG 10.3.A (last modified 19 August 2026): CASTs apply "prior to the first operational use of the cryptographic algorithm". A module with LMS signature generation must also implement key generation and have CASTs for both; a module that verifies LMS must have a CAST for verification; XMSS has the same wording; an ML-DSA verification CAST is required if the module verifies. For the hash-based schemes one parameter set (for example the lowest tree height) is enough for the CASTs, but the underlying hash function CASTs are still required. The pairwise consistency test (PCT) for SP 800-208 key pairs "may be limited to confirming the same key identifier (I in the case of LMS, SEED in the case of XMSS and PK.SEED for SLH-DSA) is shared by the resulting public and private key following generation". For key pairs rebuilt from a stored seed (FIPS 203, FIPS 204) later regenerations count as reconstitution and need no PCT.
- Module type, IG C.N Resolution 9: the signing module need not be of type hardware "Provided the hardware components of any FIPS 140-3 certified module satisfies the latter two requirements" (Level 3 or higher physical security, and a non-modifiable or limited operational environment, as quoted from SP 800-208); it "may separately include modules of type 'firmware' and 'hybrid firmware'", each supporting a Level 3 physical security claim. Software and hybrid software modules are excluded. In IG 1.B a hybrid firmware module combines firmware with a disjoint hardware component; this is unrelated to hybrid key exchange.
- What a certificate for the signing module covers: the module the lab tested, including the SP 800-208 section 8 conformance requirements (IG 10.3.A Note 8), the ban on importing private key material including "as a restore operation from a backup" (IG C.N Resolution 3), and a tester check that the module prevents using an OTS key to sign more than once (Resolution 12: "Documentation review in isolation is not sufficient"). It does not cover the on-device verification code (validated through CAVP), functions outside the module boundary of a distributed signature scheme (IG 10.3.A Note 7), or anything a bare algorithm validation implies: NIST's CAVP page says a product "does not meet the FIPS 140 module validation requirements by simply implementing an Approved security function and acquiring validations for each of the implemented algorithms."

## Two integrity checks beside the signature (Learn > Firmware PQC Migration)

NIST SP 800-193 and the FIPS 140-3 integrity test are different kinds of document. SP 800-193 is a design guideline for platforms and names no validation program. The integrity test is a requirement on a cryptographic module, tested by an accredited laboratory and validated by the CMVP.

- NIST SP 800-193, Platform Firmware Resiliency Guidelines (May 2018): aimed at developers and engineers who implement firmware-level security. Three principles: Protection keeps platform firmware code and critical data in a state of integrity, for example by ensuring the authenticity and integrity of firmware updates; Detection finds when they have been corrupted or changed from an authorized state; Recovery restores them to a state of integrity. The mechanisms are founded in Roots of Trust, defined by function: Update, Detection and Recovery. The guideline applies to any device in the platform that contains firmware; its example list for x86 platforms includes the embedded controller, TPM, baseboard management controller, SPI flash and host boot firmware.
- In an authenticated update the Root of Trust for Update holds the signature verification algorithm and the key store; both change only through an authenticated update or a secure local update. Update images must be signed with a FIPS 186-4 algorithm at a security strength of at least 112 bits. For detection the guideline lists integrity verification with a digital signature algorithm or a cryptographic hash before code outside the Root of Trust for Detection runs. The text names FIPS 186-4, which FIPS 186-5 has since superseded, and does not mention post-quantum schemes.
- FIPS 140-3 software/firmware integrity test: FIPS 140-3 takes its technical requirements and test methods from ISO/IEC 19790:2012 and ISO/IEC 24759:2017. The CMVP records changes in the SP 800-140 series and answers lab and vendor questions in the Implementation Guidance (IG). The integrity test is a pre-operational self-test (ISO/IEC 19790:2012, 7.10.2.2): the module verifies all software and firmware inside its cryptographic boundary with "an approved integrity technique or EDC", and if verification fails, the test fails. Code in non-reconfigurable memory, as the IG defines it, is exempt. The IG notes that a bootloader will have a pre-operational test for firmware integrity/authenticity.
- By security level, for the software and firmware of a hybrid module (the lesson states this list for hybrid modules only): level 1, "an approved integrity technique"; level 2, "an approved digital signature or keyed message authentication code"; levels 3 and 4, "an approved digital signature". For a hardware module, an EDC is sufficient for its software and firmware. The algorithm behind the technique first has to pass its own algorithm self-test. The Security Policy states which techniques the module uses.
- PQC signatures: the CMVP list of security functions includes ML-DSA, SLH-DSA, LMS, HSS, XMSS and XMSSMT. The IG's worked example for the integrity technique's self-test uses RSA; it gives no PQC example. The lesson states the by-level list and the CMVP list separately and does not say which PQC schemes may serve as the integrity technique at any level.

## Known-answer checks in the Firmware Signing Migrator

The known-answer area compares the engine with answers NIST published (rows tagged "NIST ACVP sample"): ML-DSA-87 verification of a NIST reference signature; for ML-DSA-87 and for ML-DSA-65 (the default) one NIST sigVer case that must verify and one that must be rejected (FIPS 204); verification of a NIST-generated SLH-DSA-SHA2-128s signature (FIPS 205); and SHA-256 and SHA-512 digests (FIPS 180-4). The checks run fixed parameter sets, not the one selected in the tool. The row tagged "Functional" (ML-DSA-87 sign + verify round trip) generates a fresh key and only checks that the engine accepts its own signature, so it has no NIST expected value. None of this establishes a validation.

6. Boot Verify Latency — splits boot signature cost into SPI flash read time (signature + public key) and software verify time on a Cortex-M4-class MCU; adjustable SPI speed (1–20 MB/s) and clock (48–408 MHz). Outputs are model estimates.

- At 2 MB/s SPI and 120 MHz: ECDSA ~8.2 ms, ML-DSA-44 ~13.7 ms, LMS ~23.4 ms, RSA-3072 ~211 ms total. Flash read is under 2 ms for every algorithm; verify time dominates.
- RSA-3072 software verify is the slowest of the four — larger PQC signatures do not make boot verify slow on an MCU.
- The 100 ms boot budget is an illustrative teaching value, not a standard; real budgets are product-specific.
- Model ignores firmware-image hashing (identical across algorithms), flash wait states, caches and crypto accelerators.
