# Ops/DevOps Quantum Impact

## Overview

The Ops/DevOps Quantum Impact module equips infrastructure operators, SREs, and DevOps engineers with the operational runbooks, configuration patterns, and monitoring tooling needed to manage PQC migration at scale. It covers six high-impact operational disruptions — certificate rotation at scale, VPN and SSH algorithm changes, monitoring threshold recalibration, CI/CD signing pipeline migration, config management template updates, and incident response for PQC-specific failures — alongside a nine-criterion ops readiness self-assessment and an Operations Playbook Builder that produces actionable runbooks. Content is calibrated for operators who manage fleets rather than write application code.

## Key Concepts

- **PQC Certificate Rotation at Scale** — public TLS certificate lifetimes are shrinking (CA/Browser Forum TLS Baseline Requirements, section 6.3.2: Subscriber Certificates issued before 2026-03-15 must not exceed 398 days, then 200 days from 2026-03-15, 100 days from 2027-03-15 and 47 days from 2029-03-15; 90-day certs are a Let's Encrypt practice, not a baseline maximum); at 10,000 certificates on 90-day cycles, rotation events increase 4× compared to 1-year classical certs; Let's Encrypt's published post-quantum plan is Merkle Tree Certificates (staging late 2026, production 2027), with ML-DSA X.509 only tracked; EST (RFC 7030) is the preferred enrollment protocol for enterprise and device fleet PQC certificate automation
- **VPN/SSH Algorithm Negotiation Changes** — strongSwan IKEv2: add ML-KEM as an additional key exchange with the `keN_` prefix, e.g. `ike=aes256gcm16-prfsha384-x25519-ke1_mlkem768` (keywords `mlkem512`, `mlkem768`, `mlkem1024`; `X25519MLKEM768` is a TLS group name, not a strongSwan keyword); OpenSSH `KexAlgorithms`: add `mlkem768x25519-sha256` (OpenSSH 9.9+, default from 10.0; OpenSSH 9.0–9.8 default PQC KEX was `sntrup761x25519-sha512`); IPsec kernel modules may require updates for new KEM ciphersuites; SSH host key rotation from ECDSA to ML-DSA requires `known_hosts` re-provisioning across all client fleets — coordinate with config management before cutting over
- **Monitoring Threshold Recalibration** — for the X25519MLKEM768 TLS 1.3 group, the client key_exchange share is 1,216 bytes (32-byte X25519 public value + 1,184-byte ML-KEM-768 encapsulation key), and the server share is 1,120 bytes (32-byte X25519 public value + 1,088-byte ML-KEM-768 ciphertext): 2,336 bytes together, excluding KeyShareEntry/extension framing and all other handshake fields. By comparison, X25519 alone contributes 32 + 32 = 64 share bytes; the hybrid shares add 2,272 bytes. Measure total handshake bytes and latency separately with the actual certificate chain, extensions, resumption mode and peer implementation; network byte-rate, connection-timeout and transaction-size thresholds may need recalibration against measured workload and service budgets. Collect the negotiated group separately from the cipher suite using documented fields in the selected TLS endpoint/logging tool; the worked OpenSSL check below demonstrates the distinction without inventing an exporter metric; recalibrate: TLS handshake size and latency alert thresholds (hybrid ML-KEM makes handshake messages larger, and hybrid IKEv2 adds an IKE_INTERMEDIATE round trip; re-baseline from your own measurements), max HTTP header size (8 KB → 32 KB for ML-DSA JWT tokens), TLS record size limits
- **CI/CD Signing Pipeline Migration** — cosign (Sigstore): Sigstore says (June 2025) it wants to enable post-quantum signing as soon as possible and gives no production date; Notation (Notary Project): ML-DSA support unconfirmed; Docker Content Trust and the Notary v1 service are being retired (full shutdown 8 December 2026; Docker names Sigstore/Cosign and Notation as the alternatives); GitHub Actions artifact signing: depends on Sigstore; migration sequence: choose a signing tool that documents ML-DSA support → update pipeline YAML → update admission controller policy → retire cosign ECDSA keys
- **Config Management PQC Defaults** — Terraform AWS provider: `key_spec = "ML_DSA_44"` (AWS KMS has offered the ML_DSA_44 key spec since June 2025; confirm that your pinned Terraform AWS provider version accepts it); Ansible crypto modules: `openssl_privatekey` with `type: ML-DSA` requires community.crypto >= 2.20; Puppet/Chef: crypto policy class updates for `crypto-policies` (RHEL) or `/etc/ssl/openssl.cnf` (Debian/Ubuntu); in the maintained nginx/OpenSSL 3.5+ example, configure TLS 1.3 cipher suites separately from key-exchange groups: `ssl_protocols TLSv1.3;`, `ssl_conf_command Ciphersuites TLS_AES_256_GCM_SHA384:TLS_AES_128_GCM_SHA256;`, and `ssl_conf_command Groups X25519MLKEM768:X25519:P-256;` (`ssl_conf_command` requires nginx 1.19.4+). This retains the TLS Basics example’s explicit classical fallback: inspect the negotiated group, because a configured hybrid option does not mean every connection used it. Certificate signatures are configured separately. See the executable sample below and the complete [TLS configuration example](/learn/tls-basics?tab=exercises)
- **PQC Incident Response Runbooks** — new failure modes requiring dedicated runbooks: (1) TLS negotiation policy checks (monitor the negotiated key-exchange group and compare it with the configured policy; TLS_AES_256_GCM_SHA384 can remain the cipher suite with either X25519MLKEM768 or X25519, so the cipher-suite name alone cannot detect this change. The worked example explicitly permits classical fallback: observing X25519 is not by itself evidence of an attack or policy violation), (2) oversized PQC handshake causing MTU fragmentation and connection failure (diagnosis: packet capture + `openssl s_client -msg`), (3) HSM unavailable during an HSM-required new-key request: keep the failed request pending; a software key plus an audit record does not meet that custody requirement. Resume through a supported HSM path and inspect its actual operation result and key object. The worked local decision check below models a new-key response, not hardware failover or recovery of an old key, (4) certificate-chain delivery exceeds a device’s TLS budget: measure the encoded chain and receiver’s decompressed-message/memory limits, then test negotiated TLS 1.3 certificate compression (RFC 8879) when both peers support it. The retained fictional ML-DSA-65 leaf-plus-intermediate sample is 11,100 bytes as a Certificate handshake and 10,913 bytes as a zlib-level-6 CompressedCertificate handshake; decompressing restores the original 11,096-byte Certificate body. An illustrative 11,000-byte uncompressed-body cap still rejects it, even though its compressed handshake is smaller than that number. These are serialization measurements, not device or compression-negotiation results. OCSP must-staple requires certificate-status evidence; it does not shrink the chain. Diagnose status-policy failures separately and test supported chain/configuration alternatives without weakening certificate validation, (5) JWT header size rejected by API gateway (fix: increase `large_client_header_buffers` in nginx or equivalent)
- **ACME/EST for PQC Certs** — ACME v2 challenge types (HTTP-01, DNS-01, TLS-ALPN-01) work unchanged for PQC certificates; the only change is the key algorithm requested in the CSR; cert-manager currently supports only RSA/ECDSA/Ed25519 key algorithms (no PQC values yet); EST (`/.well-known/est/simpleenroll`) supports PQC CSRs when the CA backend (EJBCA, Vault PKI, ADCS) supports ML-DSA
- **OPA/Kyverno Policy Enforcement** — OPA Gatekeeper ConstraintTemplate blocks admission of workloads referencing quantum-vulnerable signing keys; Kyverno ClusterPolicy can enforce approved key algorithms in cert-manager Certificate resources (PQC algorithm values are not yet available in cert-manager); TLS negotiation monitoring: compare the observed group with the allowed-group policy, as in the worked OpenSSL example. A cipher-suite regex for ECDHE/RSA does not classify TLS 1.3 key exchange; both demonstrated groups use TLS_AES_256_GCM_SHA384. Map actual documented log/exporter fields and test their collection before implementing a monitoring rule; do not treat a missing observation as a compliant connection; policy deployment strategy: Audit mode for 2 weeks → enforce mode; never enforce without a 24h rollback window
- **Envelope Re-encryption at Scale** — in the existing AWS runbook example, move an RSA-wrapped DEK to a symmetric AES-256 KMS key with `aws kms re-encrypt --ciphertext-blob fileb://dek.enc --source-key-id <old-rsa-key-id> --source-encryption-algorithm RSAES_OAEP_SHA_256 --destination-key-id <aes-256-key-id>`. This operates on one compatible KMS ciphertext blob per request; bounded batches, checkpoints and retries are orchestrated by the calling application. For the illustrative inventory of 1M wrapped DEKs, track each item’s outcome and remaining work rather than assume a measured throughput or universal bottleneck. ML-KEM KMS keys instead use `Encapsulate`/`Decapsulate` to establish a shared secret; they are not `ReEncrypt` destinations or a drop-in wrapped-DEK ciphertext format; the maintained HashiCorp Vault runbook uses `vault write transit/rewrap/<name> ciphertext=<ct>` to rewrap ciphertext with the latest version of the same named AES-256-GCM96 key. Track caller-correlated item outcomes and remaining old-version items; operation duration does not establish migration backlog. Preserve bounded batches, checkpoints and retries rather than infer progress from a latency histogram

## Worked Operations Checks

### TLS suites and groups are separate controls

With the installed OpenSSL 3.5+ build, create a one-day fictional localhost certificate/key: `openssl req -x509 -newkey rsa:2048 -noenc -days 1 -subj /CN=localhost -addext subjectAltName=DNS:localhost -keyout sample-key.pem -out sample-cert.pem`. This RSA test certificate deliberately keeps authentication separate from hybrid key exchange. In one terminal, `openssl s_server -accept 127.0.0.1:8443 -cert sample-cert.pem -key sample-key.pem -tls1_3 -ciphersuites TLS_AES_256_GCM_SHA384:TLS_AES_128_GCM_SHA256 -groups X25519MLKEM768:X25519:P-256 -www`. In another, `openssl s_client -connect 127.0.0.1:8443 -servername localhost -CAfile sample-cert.pem -verify_hostname localhost -verify_return_error -tls1_3 -ciphersuites TLS_AES_256_GCM_SHA384 -groups X25519MLKEM768 -brief` checks the hybrid path. Repeat with `-groups X25519` to exercise the explicitly permitted classical fallback. Inspect the TLS version, selected cipher suite, negotiated group and certificate verification independently. As a contrary case, supplying `X25519MLKEM768` as a `-ciphersuites` value is rejected: a TLS group is not a cipher suite. The sample permits both demonstrated groups; an unexpected group must be assessed against the configured policy, and a failed handshake provides no negotiated-group success. This OpenSSL sample tests those controls; it does not run nginx, establish PQC certificate signatures or measure fleet performance. Test the complete nginx configuration with `nginx -t` and an actual connection against the linked nginx/OpenSSL build in your own sample environment.

Sources: [nginx SSL configuration commands](https://nginx.org/en/docs/http/ngx_http_ssl_module.html#ssl_conf_command), [OpenSSL 3.5 configuration controls](https://docs.openssl.org/3.5/man3/SSL_CONF_cmd/), [X25519MLKEM768 share encoding](https://www.rfc-editor.org/rfc/rfc10024.html), [TLS certificate compression framing and limits](https://www.rfc-editor.org/rfc/rfc8879.html#section-4), [TLS Feature / OCSP status requirement](https://www.rfc-editor.org/rfc/rfc7633.html#section-4).

### Same-key rewrap accounting

The Learn tab's local worked check uses an authored inventory: A and B are at version 1 of sample-app; C is already at target version 2. Record A success using the documented response shape `data.ciphertext = "vault:v2:abcdefgh"`, then B failure: the ledger has **2 of 3 recorded at target version; 1 remaining**. Repeating A gives no extra completion credit. Retrying B with a valid correlated version-2 response reaches 3 of 3. Unknown items, wrong request-key associations, failed operations, missing ciphertext and malformed or unexpected versions receive no completion credit. The caller binds each response to the requested item and key; a ciphertext prefix does not identify a key or authenticate the payload. These are fictional observation fixtures, not responses from a running Vault server or proof of a real migration.

Use the [maintained KMS migration commands](/learn/kms-pqc?tab=workshop&step=4) for the existing AES-256-GCM96 create/rotate/rewrap sequence. In your own tools retain the correlated per-item result, returned version, checkpoint and retry state. A core route-duration metric measures request time, not the number of old ciphertexts left in the caller's inventory. Source: [Vault Transit rewrap API](https://developer.hashicorp.com/vault/api-docs/secret/transit#rewrap-data); this source describes same-key rewrap, not adoption of a new Vault edition or ML-DSA signing profile.

### HSM-required new-key request

The Learn tab also executes a local decision rule for the existing HSM-required ML-DSA-65 signing scenario. An authored generation error leaves the request pending. A modeled software key is refused even when its audit record exists; an audit record without a successful HSM key handle also leaves the request pending. An explicitly modeled restored-HSM response completes only this new-key request. No server or HSM operation executes in this decision check. A handle alone does not establish hardware custody, recovery of an old key, preservation of key identity or high availability.

The [PKCS#11 sample operations](/learn/hsm-pqc?tab=workshop&step=0) separately execute software-token generation/sign/verify operations and report their actual errors; they are not hardware failover evidence. In your own production tool inspect the operation result, provider, returned key object and required sensitive/non-extractable attributes. Restore the supported HSM path or follow the applicable recovery procedure while retaining the original custody requirement; an audit trail cannot make a software substitute equivalent.

## Workshop / Interactive Activities

The workshop has 3 interactive steps:

1. **Threat Impact Explorer** — six-panel operational briefing: certificate rotation scale calculator (input: cert count + validity period → output: rotations/day, ACME request rate, cert-manager replica sizing), VPN/SSH migration checklist with config snippet diffs for strongSwan and OpenSSH, monitoring threshold recalibration guide with before/after values for the most common alert rules, CI/CD signing migration decision matrix (cosign vs. Notation vs. GPG with PQC readiness dates), config management template update library (Terraform/Ansible/Puppet/Chef PQC patterns), and PQC incident response runbook catalog (5 failure mode runbooks with diagnosis steps)
2. **Self-Assessment Survey** — nine-criterion ops readiness evaluation covering: manages TLS certificate fleet at scale (>500 certs), owns VPN infrastructure (IPsec/IKEv2 or OpenVPN), manages server OS fleet (RHEL/Ubuntu/Windows Server), uses config management tools (Terraform/Ansible/Puppet/Chef), owns CI/CD pipelines with artifact signing, operates certificate automation (ACME/EST endpoints), runs SIEM/monitoring with crypto-specific alerting, operates HSMs in production (Luna/nShield/CloudHSM), manages cloud key management (AWS KMS/Azure Key Vault/GCP KMS); outputs an operational risk tier with sequenced remediation priorities
3. **Operations Playbook Builder** — generates a structured PQC operations playbook with four sections: (1) Certificate Lifecycle Runbook — ACME/EST enrollment config, cert-manager YAML templates, rotation schedule calculator, alert thresholds; (2) VPN/SSH Migration Runbook — strongSwan IKEv2 config diffs, OpenSSH KexAlgorithms update, `known_hosts` re-provisioning steps, rollback procedure; (3) Monitoring Configuration — Prometheus scrape config, TLS group-observation checks (see the worked OpenSSL example) and documented certificate-expiry signals, SIEM query templates (Splunk/Elastic/Datadog); (4) CI/CD Signing Migration Steps — Notation ML-DSA plugin deployment, Kyverno policy update, cosign deprecation timeline; exports as Markdown with copy-paste-ready config blocks
