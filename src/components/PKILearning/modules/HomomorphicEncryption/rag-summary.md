# Homomorphic Encryption (FHE) & HSM Key Custody

## Overview

This advanced Hardware Infrastructure module (LM-076) was split out of LM-019 _Confidential Computing & TEEs_. It covers fully homomorphic encryption (FHE) as the way to protect data in use by trusting mathematics instead of hardware, and how an HSM can hold the FHE secret key, and what its decryption policy can and cannot protect. TEEs, remote attestation and the TEE-HSM channel stay in LM-019.

One ~45-minute route: nine learn sections in learning order (what FHE is and promises; schemes, data types and noisy results; where FHE is used; the cost and how it is being reduced; keys, operations and AES data; the quantum threat; standards and compliance; the HSM as key custodian; open-source implementations), eight exercises and two workshop steps (eight flow scenarios and six hands-on concept views).

## Key Concepts

- **FHE trusts mathematics, a TEE trusts hardware** (not sourced in the Library) — the server computes directly on ciphertexts and never sees input or output, and there is no enclave to attest. The cost is speed (orders of magnitude slower than computing in the clear). FHE does not prove the result is correct: ciphertexts are malleable.
- **What "fully homomorphic" promises** — Gentry (STOC 2009): a scheme "that allows one to evaluate circuits over encrypted data without being able to decrypt". It does not promise exact results (CKKS is approximate), speed (the ICO: "several thousand times slower than processing plaintext"), integrity (NCSC: FHE provides "only confidentiality"), or that decrypted results can be shared freely.
- **Four schemes in ISO/IEC 28033 (drafts)** — BGV and BFV (exact integers, ISO/IEC 28033-2), CKKS (approximate real and complex numbers, 28033-3) and TFHE/CGGI with FHEW (bits and small integers, 28033-4; the part is titled look-up-table evaluation). The Library records ISO/IEC 28033 as under development; the current stage of each part is not sourced in the Library. Every ciphertext carries noise that grows with each operation; bootstrapping refreshes it. CKKS is fixed-point approximate arithmetic: read results by rounding to a trusted precision.
- **Which scheme for which data** — BFV/BGV for exact values (counting, matching, private lookups), CKKS for real numbers and machine-learning inference, TFHE for comparisons and lookup-table logic (Microsoft SEAL README).
- **Where FHE is used** — in production for private lookups (Apple, BFV) and Microsoft Edge's password breach check (SEAL); peer-reviewed for private set intersection, genome-wide association studies, biometric search and AI inference; small, slow AI training; pilots for official statistics; a regulator sandbox for cross-border financial-crime intelligence. The sources show it used where a small query or simple computation can wait seconds to hours and the data could not otherwise be shared.
- **Cost and acceleration** — reported overheads range from thousands of times (ICO) to about a million times (DARPA estimate, 2021). GPUs, FPGAs, simulated and fabricated accelerator chips and better algorithms report large speedups, each against its own baseline; no source shows DARPA DPRIVE's within-ten-times goal met. TEEs, MPC, differential privacy and federated learning trade cost against different trust assumptions.
- **Standards and compliance** — FHE is not among FIPS 140-3 approved security functions, has no generally approved CNSA 2.0 solution and no Common Criteria certification; only the conventional cryptography around it can be validated. The HomomorphicEncryption.org Security Standard v1.1 (2018) is a community standard. Under the GDPR, encryption is not anonymisation (EDPB draft Guidelines 02/2026).
- **One small secret key, many large public keys** — the secret key can be regenerated from a 32-byte seed; the public encryption, relinearization, rotation and bootstrapping keys are large and need integrity protection. There is no standard encoding yet: no PKCS#11 or KMIP object type and no X.509 OID.
- **FHE does not work directly with AES** — an AES ciphertext has no structure a server can compute on. Transciphering runs the symmetric cipher's decryption inside FHE; TFHE-rs ships it for Kreyvium and AES-128-CTR.
- **Quantum threat** — lattice-based FHE has no known quantum break (it rests on the (Ring-)Learning With Errors family behind ML-KEM). The parts around the scheme, such as classical key exchange and signatures on the key set, are usually still classical and need a post-quantum fix.
- **The HSM as FHE key custodian** — generate a non-extractable 32-byte seed in the HSM, derive the secret key inside it, sign the parameter set and evaluation-key hashes with ML-DSA, decrypt under policy with an audit log, and back the seed up only HSM to HSM. The HSM can run key generation and decryption but not homomorphic evaluation. A bootstrappable CKKS evaluation-key set (3.94 GB as exported) streams out of the token in 1,001 bounded calls: measured 473 s on one MX95 Cortex-A55 core with a 16.7 MiB token peak, and 213.8 s on one core or 84.0 s on six MX95 Pro cores once the token caches work between calls (64.5–123.6 MiB peak; about 16 MiB at about twice the time with the cache off). On the board the CPU, not the 1 Gb/s link, is the limit (54 MB/s at best). This is a deployment pattern; no FHE library or paper defines an HSM role. No standard PKCS#11 mechanism exists.
- **The decryption-oracle limitation** — an unrestricted or insufficiently checked HSM decryption interface can become a key-recovery oracle, and decrypted CKKS results seen by others can leak key information even from honest computations. Single-HSM decryption therefore trusts the authorized release path and relies on a decryption policy (approved result shapes, rounding, noise flooding for CKKS, budgets, audit) plus compensating controls; BFV, BGV and TFHE need negligible decryption-failure probability. Measured: the flood width follows the published analysis (Li, Micciancio, Schultz and Sorrell 2022, Corollary 2: log2 sigma = s/2 + 1/2 log2(24 q n) + log2 B, q = (replicas + 1) x maximum decryptions; the first version was 10.3 bits narrower and counted one copy of the key). At CKKS default parameters, flooding for 30 bits of statistical security over 10,000 releases and four replicas needs sigma = 2^43.1 and leaves -12.8 bits in the noise-study emulation, and the token refuses the release. A second parameter set (META-BTS bootstrapping twice per refresh, scale 2^90, sigma = 2^69.1) keeps 11.10, 11.25 and 11.34 bits at program depth 0, 1 and 3 end to end on a Mac, and with the token on the boards 11.37, 11.20 and 11.26 bits (MX95 Pro) and 11.19, 11.14 and 11.32 bits (MX95), within 0.3 bits of the Mac, against a bar of 10 bits: a thin margin of about 1.1-1.4 bits, set by the paper's exact sizing, at about twice the bootstrap time, 3 multiplications between refreshes instead of 9 and a 12 % larger key set. Each board generated the 4.41 GB key set in 96.9 s (MX95 Pro) and 99.2 s (MX95), with every limb equal to the reference. The earlier board runs at the narrower width (22.78 bits on the MX95 Pro, 22.59 on the MX95) are kept as records of that run. The noise is drawn with floating-point Box-Muller and rounded: the time of one draw depends on the value drawn (about 21 ns of 230-390 ns, measured on both MX95 boards), the time of a whole release showed no measurable dependence, the noise is a rounded continuous Gaussian rather than the discrete Gaussian of the published analysis, and a constant-time sampler is a tracked next-development item. Threshold decryption removes the single point of trust at the cost of more parties and ceremony.
- **Threshold FHE** — split the key across several parties so no single decryptor exists. OpenFHE (BFV, N-of-N) and Lattigo (BGV, t-of-N) implement it. For CKKS, a 2-of-2 Lattigo prototype at the real parameters works (joint keys bootstrap at 24.3–24.5 bits; 4.10 GB of shares per party), but flooding for third parties at the default parameters fails as with one token (the corrected width is wider, so it fails by more), and a crafted request sent to one party returns that party's whole share, so each token needs its own independent approval. One share alone decrypts nothing (-27.8 bits); the joint secret has about 384 non-zero coefficients against 192; a decryption share at level 0 is 0.5 MB (1.05 MB switched to the owner's public key). Key-recovery attacks have been reported on t-of-N threshold decryption (IACR ePrint 2026/031, preprint); t-of-N such as 2-of-3 is not recommended, and whether the attacks apply to a fixed 2-of-2 split is not established.
- **Key rotation without decrypting stored data** — the token streams one key-switching key from the old secret to a new token-generated one (31.5 MB, byte-identical to Lattigo), and the FHE server switches stored ciphertexts to the new key (precision 28.7 → 27.1–27.3 bits). Security officer only; the old seed is retired after the rotation manifest is signed, and the token commits a signed retirement record before it destroys it; the server deletes the rotation key. The token refuses a user or public session, the same seed, a different parameter set, a copy of a token-made key as the new secret, going back from new to old, a second target for the same old secret, and a looser decryption policy. One switch took 36.5 ms at the top level and 10.1 ms at level 0 on a Mac. Not established: whether a holder of the old secret can read switched ciphertexts without the original.
- **Cross-checks with other libraries** — OpenFHE v1.6.0 CKKS at N = 2^16 (128-bit-checked settings): 80 keys, 13.26 GB, one bootstrap at 13.3 bits; That run counted one test rotation; the keys bootstrapping needs are 79, 13.09 GB. Lattigo-layout keys ran in OpenFHE with equal precision through a format bridge. The HSM's own key export now runs in OpenFHE as it is: a third parameter set (registry ID 4) takes OpenFHE v1.6.0's primes, digits and key list at its 128-bit-checked settings; the token streamed all 79 keys (6.56 GB) in 17.8 s on an M5 Max with an 83.5 MB peak, 0 mismatches over 12,483 evaluation-key limbs, and OpenFHE bootstrapped once, its default refresh, with only the token's keys at 13.28 bits against 13.20 with its own; owner release only. OpenFHE's iterative bootstrapping (two rounds: EvalBootstrap with numIterations 2 and a precision argument) works with the same 79 keys, nothing changed on the token, and raises the precision: one round 13.2 bits; two rounds 21.1 bits at the setting OpenFHE's example recommends (precision 8, the measured bits minus 5) and 31.7 to 31.8 bits at the best settings found (precision 19 to 20; a freshly encrypted ciphertext is 32.1 bits in the earlier run); through the token's owner release 30.5 bits when the ciphertext's true scale is applied and 27.0 bits when the release is read at face value, because OpenFHE's scale after a bootstrap differs from 2^52 by 6 to 7 parts in a billion and the token's input carries the scale only as a power of two. Below precision 19 the result is about 13.2 plus the precision; above 20 it falls (28.0 at 22, 24.2 at 24; not investigated); the best setting came from a sweep, not from a documented rule. The token's keys and OpenFHE's own agree within 0.4 bit. The cost is about twice the time (about 6 s against 3.2 s on a shared Mac) and one level (7 left instead of 8; keeping 8 needs a chain depth that OpenFHE refuses at N = 2^16; it asks for N = 2^17); peak memory is unchanged at 16.6 GiB. One Mac, no board, one seeded input, four runs per setting up to precision 15 and two above, the variant that raises the modulus first only. The token's export of this set was also generated on both MX95 boards in 145 s (MX95) and 142 s (MX95 Pro), about 2.4 minutes each, and streamed to a Mac in about 3 minutes (181 s and 178 s), with all 1,565 pieces matching the reference and the token-signed manifest; OpenFHE itself ran only in a container on a Mac, not on a board. Lattigo reproduces Microsoft SEAL v4.1.2 CKKS decryptions exactly. TFHE-rs 1.8.1 published test vectors: 28 of 36 byte-identical on a Mac and both MX95 boards; the 8 FFT outputs differ from upstream bytes but are identical across our platforms and decrypt correctly.
- **An encrypted risk-scoring service** — a reference service scores 32,768 customers per request on CKKS ciphertexts made under the token's keys (logistic regression on the UCI credit-default dataset, CC BY 4.0; a cubic in place of the sigmoid, 3 multiplications, no refresh). On 6,000 held-out rows: AUC 0.717298 encrypted against 0.717299 in plaintext and the same decision on all 32,768 slots; about 200 ms of server time per batch on an M5 Max, while encrypting a batch takes the data owner 3.6 s. The same service, built as a static binary for each processor, also ran on an x86-64 virtual machine (12 virtual CPUs of an AMD Ryzen AI 9 HX 370, token in a container on the Mac: 277 ms per batch, median of three repetitions, 273-305 ms over all 8 jobs; server peak 1,311 MiB; key set admitted with 40 ms to verify and 100 ms to assemble; about 13,000 requests an hour by server time alone; whole run 47 s) and on an MX95 Pro board (6 Cortex-A55 cores, 15.4 GiB) with the token on the base MX95 board, which exported its 4.41 GB key set in 124 s (35.7 MB/s, 83 MiB peak): 4.29 s per batch (median of three, 4.16-4.66 s over all 8 jobs), about 21 times the Mac; server peak 1,870 MiB; key set admitted with 170 ms to verify and 497 ms to assemble; 600 requests an hour one at a time with the 184 MiB upload and 840 by server time alone; whole run 202 s. The scores were identical on all three machines (21.00 bits against the plaintext cubic, the same decision on every slot at 0.5 and 0.25, AUC 0.717298 against 0.717299). The service admits keys only with the token's ML-DSA-65-signed manifest, needs only the relinearization key, speaks TLS 1.3 with X25519MLKEM768 and a client certificate, and refuses about 40 tested bad inputs; only the owner can decrypt a score (owner release). Limits: classical test certificates, one tenant, memory only, 3 multiplications and one batch size, one run per machine; the first virtual machine run and the board run use the published test seed (a third run, on the virtual machine with the token on the MX95 Pro reached over KMIP, used a random seed generated in the token and gave the same accuracy) (the secret key is public, so they measure time, memory and correctness, not secrecy), the x86 run is a virtual machine whose cores were not pinned, and the board's service listens on loopback behind an ssh tunnel with TLS inside it.

## Workshop / Interactive Activities

_FHE + HSM Flows_: step through eight scenarios (CKKS and TFHE single-HSM custody, OpenFHE and Lattigo threshold FHE, what fits in the HSM, Kreyvium transciphering, CKKS key rotation, and CKKS shared 2-of-2 decryption). Each step shows who holds which key and which data state, and a quantum overlay marks the links a quantum computer breaks.

_FHE concepts, hands-on_: six interactive views (noise budget and bootstrapping, encoding and rounding, programs as FHE circuits, key streaming and chunk size, key rotation without decrypting, shared 2-of-2 decryption). In the key-rotation view the user picks who starts a rotation and what the new secret is and sees what the token refuses; in the shared-decryption view the user toggles independent approvals and flooding and sees the measured outcome.
