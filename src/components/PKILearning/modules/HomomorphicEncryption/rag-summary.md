# Homomorphic Encryption (FHE) & HSM Key Custody

## Overview

This advanced Hardware Infrastructure module (LM-076) was split out of LM-019 _Confidential Computing & TEEs_. It covers fully homomorphic encryption (FHE) as the way to protect data in use by trusting mathematics instead of hardware, and how an HSM can hold the FHE secret key, and what its decryption policy can and cannot protect. TEEs, remote attestation and the TEE-HSM channel stay in LM-019.

One ~45-minute route: nine learn sections in learning order (what FHE is and promises; schemes, data types and noisy results; where FHE is used; the cost and how it is being reduced; keys, operations and AES data; the quantum threat; standards and compliance; the HSM as key custodian; open-source implementations), eight exercises and one workshop step with six scenarios.

## Key Concepts

- **FHE trusts mathematics, a TEE trusts hardware** — the server computes directly on ciphertexts and never sees input or output, and there is no enclave to attest. The cost is speed (orders of magnitude slower than computing in the clear). FHE does not prove the result is correct: ciphertexts are malleable.
- **What "fully homomorphic" promises** — Gentry (STOC 2009): a scheme "that allows one to evaluate circuits over encrypted data without being able to decrypt". It does not promise exact results (CKKS is approximate), speed (the ICO: "several thousand times slower than processing plaintext"), integrity (NCSC: FHE provides "only confidentiality"), or that decrypted results can be shared freely.
- **Four schemes in ISO/IEC 28033 (drafts)** — BGV and BFV (exact integers, ISO/IEC DIS 28033-2), CKKS (approximate real and complex numbers, FDIS 28033-3) and TFHE/CGGI with FHEW (bits and small integers, FDIS 28033-4; the part is titled look-up-table evaluation). No part is published yet; parts 3 and 4 entered their final ballots in September 2026. Every ciphertext carries noise that grows with each operation; bootstrapping refreshes it. CKKS is fixed-point approximate arithmetic: read results by rounding to a trusted precision.
- **Which scheme for which data** — BFV/BGV for exact values (counting, matching, private lookups), CKKS for real numbers and machine-learning inference, TFHE for comparisons and lookup-table logic (Microsoft SEAL README).
- **Where FHE is used** — in production for private lookups (Apple, BFV) and Microsoft Edge's password breach check (SEAL); peer-reviewed for private set intersection, genome-wide association studies, biometric search and AI inference; small, slow AI training; pilots for official statistics; a regulator sandbox for cross-border financial-crime intelligence. The sources show it used where a small query or simple computation can wait seconds to hours and the data could not otherwise be shared.
- **Cost and acceleration** — reported overheads range from thousands of times (ICO) to about a million times (DARPA estimate, 2021). GPUs, FPGAs, simulated and fabricated accelerator chips and better algorithms report large speedups, each against its own baseline; no source shows DARPA DPRIVE's within-ten-times goal met. TEEs, MPC, differential privacy and federated learning trade cost against different trust assumptions.
- **Standards and compliance** — FHE is not among FIPS 140-3 approved security functions, has no generally approved CNSA 2.0 solution and no Common Criteria certification; only the conventional cryptography around it can be validated. The HomomorphicEncryption.org Security Standard v1.1 (2018) is a community standard. Under the GDPR, encryption is not anonymisation (EDPB draft Guidelines 02/2026).
- **One small secret key, many large public keys** — the secret key can be regenerated from a 32-byte seed; the public encryption, relinearization, rotation and bootstrapping keys are large and need integrity protection. There is no standard encoding yet: no PKCS#11 or KMIP object type and no X.509 OID.
- **FHE does not work directly with AES** — an AES ciphertext has no structure a server can compute on. Transciphering runs the symmetric cipher's decryption inside FHE; TFHE-rs ships it for Kreyvium and AES-128-CTR.
- **Quantum threat** — lattice-based FHE has no known quantum break (it rests on the (Ring-)Learning With Errors family behind ML-KEM). The parts around the scheme, such as classical key exchange and signatures on the key set, are usually still classical and need a post-quantum fix.
- **The HSM as FHE key custodian** — generate a non-extractable 32-byte seed in the HSM, derive the secret key inside it, sign the parameter set and evaluation-key hashes with ML-DSA, decrypt under policy with an audit log, and back the seed up only HSM to HSM. The HSM can run key generation and decryption but not homomorphic evaluation. A bootstrappable CKKS evaluation-key set (3.94 GB as exported) streams out of the token in 1,001 bounded calls: measured 473 s on one MX95 Cortex-A55 core with a 16.7 MiB token peak, and 213.8 s on one core or 84.0 s on six MX95 Pro cores once the token caches work between calls (64.5–123.6 MiB peak; about 16 MiB at about twice the time with the cache off). On the board the CPU, not the 1 Gb/s link, is the limit (54 MB/s at best). This is a deployment pattern; no FHE library or paper defines an HSM role. No standard PKCS#11 mechanism exists.
- **The decryption-oracle limitation** — whoever may ask the HSM to decrypt can recover the FHE secret key, and decrypted CKKS results seen by others leak it even from honest computations. Single-HSM decryption therefore trusts every caller allowed to decrypt and relies on a decryption policy (approved result shapes, rounding, noise flooding for CKKS, budgets, audit) plus compensating controls; BFV, BGV and TFHE need negligible decryption-failure probability. Measured: at CKKS default parameters, flooding sized for 30 bits of statistical security over 10,000 releases leaves no correct bits; a second parameter set (META-BTS bootstrapping twice per refresh, scale 2^90) keeps 22.8 bits end to end on a Mac, at about twice the bootstrap time, 3 multiplications between refreshes instead of 9 and a 12 % larger key set; it is not yet measured on the boards. Threshold decryption removes the single point of trust at the cost of more parties and ceremony.
- **Threshold FHE** — split the key across several parties so no single decryptor exists. OpenFHE (BFV, N-of-N) and Lattigo (BGV, t-of-N) implement it. For CKKS, a 2-of-2 Lattigo prototype at the real parameters works (joint keys bootstrap at 24.3–24.5 bits; 4.10 GB of shares per party), but flooding for third parties fails as with one token, and a crafted request sent to one party returns that party's whole share, so each token needs its own independent approval. Key-recovery attacks have been reported on t-of-N threshold decryption (IACR ePrint 2026/031, preprint).
- **Key rotation without decrypting stored data** — the token streams one key-switching key from the old secret to a new token-generated one (31.5 MB, byte-identical to Lattigo), and the FHE server switches stored ciphertexts to the new key (precision 28.7 → 27.1–27.3 bits). Security officer only; the old seed is retired after the rotation manifest is signed.
- **Cross-checks with other libraries** — OpenFHE v1.6.0 CKKS at N = 2^16 (128-bit-checked settings): 80 keys, 13.26 GB, one bootstrap at 13.3 bits; Lattigo-layout keys ran in OpenFHE with equal precision through a format bridge, but the HSM's own exported key set has not been run in OpenFHE. Lattigo reproduces Microsoft SEAL v4.1.2 CKKS decryptions exactly. TFHE-rs 1.8.1 published test vectors: 28 of 36 byte-identical on a Mac and both MX95 boards; the 8 FFT outputs differ from upstream bytes but are identical across our platforms and decrypt correctly.

## Workshop / Interactive Activities

_FHE + HSM Flows_: step through six scenarios (CKKS and TFHE single-HSM custody, OpenFHE and Lattigo threshold FHE, what fits in the HSM, and Kreyvium transciphering). Each step shows who holds which key and which data state, and a quantum overlay marks the links a quantum computer breaks.
