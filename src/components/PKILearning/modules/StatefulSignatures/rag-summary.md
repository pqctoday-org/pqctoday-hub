# Stateful Hash-Based Signatures Module (LMS/XMSS)

The Stateful Hash-Based Signatures module covers LMS (Leighton-Micali Signature) and XMSS (eXtended Merkle Signature Scheme), the most conservative post-quantum signature schemes standardized in NIST SP 800-208. These schemes derive security solely from hash function properties, requiring no new cryptographic hardness assumptions. The module explains Merkle tree signature construction, Winternitz one-time signatures (OTS), the critical state management problem, and the trade-offs between stateful schemes (LMS/XMSS) and stateless alternatives (SLH-DSA). CNSA 2.0 approves all parameters of LMS and XMSS (NIST SP 800-208) for digitally signing firmware and software in national security systems and recommends LMS SHA-256/192.

## Key Concepts

- Security of the stateful hash-based schemes depends only on the security of the underlying hash functions, in particular the infeasibility of finding a preimage or a second preimage (SP 800-208); LMS requires second-preimage resistance of its hash function (RFC 8554 §9), and XMSS is even secure when the collision resistance of its hash function is broken (RFC 8391), although randomized hashing does not stop a signer from creating a generic collision, since the signer can choose the random value (SP 800-208 §9.2)
- Merkle tree structure: each leaf contains the hash of a unique OTS public key; the tree root serves as the overall public key; signatures include an OTS signature plus an authentication path from leaf to root
- Winternitz OTS (WOTS+): each one-time key pair signs exactly one message; the Winternitz parameter W controls a size/speed trade-off (W=1 fastest/largest, W=8 slowest/smallest) with zero impact on security level
- Catastrophic OTS reuse: signing two different messages with the same leaf enables an attacker to compute enough of the private key to forge arbitrary signatures -- a complete break requiring full key revocation
- LMS (RFC 8554): single-tree scheme with heights H=5 to H=25 (32 to 33M signatures), public keys of 24 bytes plus the hash output length (48 bytes for the SHA-256/192 sets, 56 bytes for the SHA-256 sets), signature sizes 1.3-9.3 KB; HSS extends LMS with up to 8 tree levels for massive signing capacity
- XMSS (RFC 8391): bitmask-based tree hash for multi-target attack resistance, WOTS+ OTS scheme, a security proof that does not rely on the collision resistance of the hash functions but on weaker properties (RFC 8391), and no forward security as standardised (SP 800-208 and RFC 8391 derive every one-time key from one fixed seed; forward-secure XMSS is a research variant)
- LMS vs XMSS: LMS is simpler with faster key generation (NSA CNSA 2.0 allows single-tree LMS and XMSS only, and prefers LMS with SHA-256/192); the security proof of XMSS does not rely on the collision resistance of its hash functions (RFC 8391; forward security only in a research variant, not as standardised); BSI TR-02102-1 recommends both families
- NIST SP 800-208 §8.1 requires a durable incremented leaf index before signature output or acceptance of another signing request. Section 9.1 discusses hardware monotonic counters as a possible aid, not a universal HSM implementation. The state-management exercise now explains design/code review, crash/power-loss, concurrency and recovery checks, how to interpret leaf reuse, and why finite tests or successful verification do not prove reuse impossible. The Hub does not perform hardware recovery testing or establish validated hardware.
- Stateful vs stateless comparison: LMS/XMSS require state tracking and have bounded leaf counts. SLH-DSA needs no persistent leaf counter, but the security claims for FIPS 205's 12 parameter sets assume at most 2^64 messages per key pair (§11). This analysis limit is not an LMS/XMSS-style counter requirement or a prediction of immediate failure beyond the limit. SLH-DSA has larger signatures (8-49 KB); performance depends on the parameter set and implementation.

## What the lab tests (validation)

A FIPS 140-3 certificate for a module that signs with LMS or XMSS rests on four kinds of check. The Learn tab (The State Problem step) has a "What the lab tests" panel with these facts.

- Algorithm tests (NIST ACVP, under CAVP): the ACVP specification for LMS (draft of 2 October 2026) has three modes, keyGen, sigGen and sigVer, each with one test type, AFT (Algorithm Functional Test). keyGen: generate a key pair based on an approved tree structure. sigGen: generate valid signatures based on the ACVP-provided message. sigVer: determine the validity of the signature given the tree structure, key and message. A vendor registers LMS modes and LM-OTS modes by hash, tree height (for example LMS_SHA256_M24_H5 through LMS_SHA256_M32_H25) and Winternitz setting (W1, W2, W4, W8); the pair must follow SP 800-208 Section 4, "namely M = N, and the hash is the same". The CAVP prerequisites page lists "All hash functions and XOFs used." for LMS keyGen, sigGen and sigVer.
- What ACVP does not test, in the specification's words: "ACVP does not test the inability of an implementation to export a private key. ACVP does not provide any guarantees on the inability to reuse private OTS pairs of an implementation."
- XMSS, XMSS^MT and HSS: no ACVP specification is published for them (the ACVP index at pages.nist.gov/ACVP lists LMS, ML-DSA, ML-KEM and SLH-DSA as its post-quantum entries, checked 23 October 2026). FIPS 140-3 IG C.N, last modified 10 September 2024, says CAVP tests are "available for LMS but not yet for XMSS, HSS, or XMSSMT". IG C.O (same date) records that "Support for the LMS scheme was added to the ACVTS production server in April 2023" and that "the other schemes (including HSS) remain untestable by the CAVP as of the last modified date of this IG".
- Module self-tests (FIPS 140-3 IG 10.3.A item 5, document updated 19 August 2026): cryptographic algorithm self-tests (CASTs) apply "prior to the first operational use of the cryptographic algorithm". A module that implements LMS (or HSS, XMSS, XMSS^MT) signature generation must also implement key generation and have CASTs for both; signature verification needs its own CAST; the HSS CASTs cover the LMS ones and the XMSS^MT CASTs cover the XMSS ones. A CAST for SHA-256 is required; for SHA-256/192 if implemented without SHA-256; for SHAKE256/256; for SHAKE256/192 if implemented without SHAKE256/256 (satisfiable inside the higher-level CASTs). Because testing cost depends on tree height, the CASTs need only exercise the smallest (or any single) supported parameter set, and "It is also not necessary to test both LM-OTS + LMS modes"; a CAST covering the different underlying SHA or SHAKE functions is still required. The pairwise consistency test for SP 800-208 keys "may be limited to confirming the same key identifier (I in the case of LMS, SEED in the case of XMSS and PK.SEED for SLH-DSA) is shared by the resulting public and private key following generation".
- What the certificate covers: SP 800-208 §8.1 says "Implementations of the key generation and signature algorithms in this document shall only be validated for use within hardware cryptographic modules", with Level 3 or higher physical security, a non-modifiable or limited operational environment, approved mode only with no bypass mode, no export of private keying material, and the entropy source inside the physical boundary. IG C.N resolution 9: where the hardware components of a certified module meet the Level 3 physical security and the non-modifiable or limited operational environment, "it is not required that modules are module type: 'hardware' and may separately include modules of type 'firmware' and 'hybrid firmware'"; software and hybrid software modules are excluded. IG C.N resolution 1: the §8.1 requirements "exclusively apply to modules supporting HBS key generation and signature generation"; modules that only support signature verification "need to comply with requirements from section 8.2 of SP 800-208, but do not need to meet requirements from section 8.1".
- What the lab checks where ACVP is silent (IG C.N): no import of HBS private keys, including "importing private keys as a restore operation from a backup" (resolution 3); no external entropy source outside the hardware perimeter for key generation (resolution 5); no "independent copies of keys internal to the cryptographic boundary" (resolution 7). The vendor "shall justify the implementation strategy taken to eliminate the possibility of OTS private key re-use" (resolution 11). "Documentation review in isolation is not sufficient"; the tester confirms the module prevents the use of an OTS key to generate a digital signature more than one time, cannot create an independent copy of an HBS key, and, if it stores keys in non-volatile memory, updates the leaf index there before exporting a signature value or accepting a request to sign another message (resolution 12).
- CNSA 2.0 (NSA CNSA 2.0 FAQ, version 2.2, October 2026): LMS and XMSS (NIST SP 800-208) are listed for digitally signing firmware and software with "All parameters approved for all classification levels. LMS SHA-256/192 is recommended." HSS and XMSS^MT are "not allowed". SLH-DSA "is not part of CNSA and is not approved for any use in NSS". Verifier and signer are validated differently. A product that only verifies signatures: "If your product is only verifying signatures, CAVP testing is all that is required." Signers that are NSS "are required to produce signatures according to NIST SP 800-208, which requires hardware validated by NIST's Cryptographic Module Validation Program (CMVP), or via other NSA guidance. Waivers for this will not be granted." Signers that are not themselves NSS (for example a commercial vendor's build environment) are "expected to use code in their signature generation processes that is at least at the same operational quality as the code being put on the device, but the only part NSA will validate is that the signature verification code on the device passes CAVP." For products evaluated under a NIAP Protection Profile where signing occurs outside the Target of Evaluation boundary, "if only signature verification is being performed only CAVP validation (not CMVP) will be expected to meet CNSA 2.0 for such products." The FAQ also says signing and state management should be implemented in hardware such as an HSM, and backup flows "must prevent state re-use".

## Workshop Activities

- **Step 1 -- LMS Key Generation**: Explore LMS parameter sets (tree height, Winternitz W, hash function), visualize Merkle tree structure, and compare key and signature sizes across configurations
- **Step 2 -- XMSS Key Generation**: Compare XMSS with LMS at equivalent security levels, examine bitmask construction and L-tree compression, and analyze the performance and size trade-offs
- **Step 3 -- State Management Visualizer**: Sign with a real HSS key in the in-browser HSM, read the leaf counter from the engine, and run the key to exhaustion. "Simulate State Loss" asks the HSM to take the key back to an earlier signature, the three ways a restore or clone would (write the leaf counter back, read the key state out, copy the key), and prints the PKCS#11 reply to each: this engine answers CKR_ATTRIBUTE_READ_ONLY, CKR_ATTRIBUTE_SENSITIVE and CKR_ACTION_PROHIBITED, so no leaf is reused and the counter stays consistent with the signature log. That is how this emulator behaves; it does not show that any certified module does the same. The page also names the leaves that a signer keeping its state in an ordinary file or VM image would have made available again, because SP 800-208 section 1.2 says that signatures on two different messages from one OTS key make forgery computationally feasible.
- **Step 4 -- SLH-DSA Live Demo, size comparison and algorithm checks**: Generate real SLH-DSA keys over PKCS#11 and compare LMS, SLH-DSA and ML-DSA by named parameter set, not by security level (SP 800-208 assigns no NIST category to LMS): LMS_SHA256_M24_H10 / LMOTS_SHA256_N24_W4 has a 48-byte public key and a 1,500-byte signature; SLH-DSA-SHA2-192s 48 B and 16,224 B (FIPS 205 Table 2); ML-DSA-65 1,952 B and 3,309 B, ML-DSA-87 2,592 B and 4,627 B (FIPS 204 Table 2). The LMS sizes follow RFC 8554 (public key 4 + 4 + 16 + m bytes, signature 12 + n(p + 1) + m*h bytes, with the SP 800-208 SHA-256/192 values n = m = 24, p = 51, h = 10); a one-level HSS key, which is what the PKCS#11 engine signs with, adds 4 bytes, so the 60-byte key in RFC 8554 Appendix F is a two-level HSS key and an LMS key with m = 32 is 56 bytes. CNSA 2.0 in that table: single-tree LMS is approved for firmware and software signing (SHA-256/192 recommended), HSS is not allowed, SLH-DSA is not approved for any use in NSS, and ML-DSA-87 is the only ML-DSA set.
- **Step 4 -- Algorithm checks**: known-answer checks and functional round trips are shown separately. The known-answer checks are LMS/HSS signature verification against RFC 8554 Appendix F Test Cases 1 and 2, a SHA-256 NIST sample, and a replay of all 16 cases of the public NIST ACVP-Server LMS sigVer samples (commit 975de31, folders LMS-sigVer-SP800-208 and LMS-sigVer-1.0; the SHA-256/192 sets LMS_SHA256_M24_H5 / LMOTS_SHA256_N24_W1 and LMS_SHA256_M24_H10 / LMOTS_SHA256_N24_W2; one valid signature and three modified ones per group). The engine, through PKCS#11 CKM_HSS with NIST's bytes behind the one-level HSS prefix, must accept the valid signatures and reject the modified message, modified signature and modified signature header cases, as NIST's expected result says. The eight SLH-DSA sigVer cases are replayed the same way. The SLH-DSA sign-and-verify rows are functional round trips, not known-answer tests: the engine verifies its own output. The ACVP samples are public reference samples, not vectors issued by an ACVTS test session, so a pass establishes no validation. LMS key generation and signature generation vectors, the SHA-256/256 and SHAKE sets, HSS and XMSS are not run.

## Related Standards

- NIST SP 800-208 (Recommendation for Stateful Hash-Based Signature Schemes, October 2020)
- RFC 8554 (LMS -- Leighton-Micali Signature), RFC 8391 (XMSS -- eXtended Merkle Signature Scheme)
- FIPS 140-3 (HSM validation for state management enforcement; Implementation Guidance 10.3.A self-tests, C.N and C.O for SP 800-208), FIPS 205 (SLH-DSA stateless alternative)
- CNSA 2.0 (permits LMS/XMSS for firmware/software signing; 2025 preference and 2030 exclusive-use milestone for that category; FAQ version 2.2 mandates CNSA 2.0 algorithms for NSS by 2031 unless otherwise noted); verify-only products need CAVP testing only, while signers that are NSS need hardware validated by CMVP or, in the FAQ's words, "via other NSA guidance", and waivers are not granted (see What the lab tests)
- RFC 10033, formerly draft-ietf-pquip-hbs-state (practical guidance on state, backup, and recovery for LMS/XMSS deployments)
- BSI Technical Guideline TR-02102-1 (recommends all SP 800-208 parameter sets of LMS/HSS and XMSS/XMSS^MT)
